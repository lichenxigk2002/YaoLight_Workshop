# 瑶光工坊 (YaoLight Workshop) - 模块化DDD架构说明

## 架构特点

瑶光工坊采用**模块化领域驱动设计**，结合微服务风格的目录组织，每个业务模块独立完整。

## 模块设计原则

### 1. 高内聚
每个模块包含完整的业务逻辑：
- **models/**: 持久化实体（GORM实体，负责数据库映射）
- **repositories/**: 仓储实现（实现 domain/repository 接口，负责数据访问）
- **services/**: 应用服务（使用 Repository 接口，实现业务逻辑）
- **controllers/**: 接口层（HTTP处理器，调用 Service）

### 领域层（domain/）
- **entity/**: 领域实体（纯业务对象，不依赖 GORM 或数据库）
- **repository/**: 仓储接口定义（定义数据访问契约）

### 2. 低耦合
- 模块间通过接口通信
- Service 依赖 Repository 接口（domain/repository），不直接依赖实现
- 领域实体（domain/entity）与持久化实体（models）分离
- 共享代码放在 `infrastructure/shared`
- 避免模块间直接依赖

### 3. 可扩展
- 新增功能只需添加新模块
- 模块内部可独立演进
- 便于后续拆分为微服务

## 数据流转（DDD 分层架构）

```
HTTP请求
  ↓
controllers/ (接口层/应用层)
  ↓
services/ (应用服务层)
  ↓
domain/repository/ (仓储接口 - 领域层)
  ↓
repositories/ (仓储实现 - 基础设施层)
  ↓
models/ (持久化实体 - 基础设施层)
  ↓
数据库

领域层：
  - domain/entity/ (领域实体，纯业务对象)
  - domain/repository/ (仓储接口定义)
```

## 优势

1. **清晰的组织结构**：每个模块职责明确
2. **易于维护**：修改某个功能只需关注对应模块
3. **便于测试**：模块可独立测试
4. **可扩展性强**：新增功能不影响现有模块
5. **便于团队协作**：不同开发者可负责不同模块

## DDD 架构优势

1. **领域驱动**：业务逻辑集中在领域实体和领域服务中
2. **依赖倒置**：Service 依赖 Repository 接口，不依赖具体实现
3. **可测试性**：可以轻松 Mock Repository 接口进行单元测试
4. **可维护性**：领域实体与持久化实体分离，业务逻辑清晰
5. **可扩展性**：可以轻松切换数据源（如从 PostgreSQL 切换到 MySQL）

## 下一步开发

1. 在 `domain/entity/` 中定义领域实体
2. 在 `domain/repository/` 中定义仓储接口
3. 在 `modules/*/repositories/` 中实现仓储接口
4. 在 `modules/*/services/` 中使用 Repository 接口实现业务逻辑
5. 在 `modules/*/controllers/` 中实现HTTP接口
6. 在 `infrastructure/middleware/` 中实现中间件
