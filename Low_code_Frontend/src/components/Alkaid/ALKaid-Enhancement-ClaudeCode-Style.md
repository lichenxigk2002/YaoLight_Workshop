# 瑶光星 · 功能增强文档（智能体与工作流进度）

> 本文档建立在《瑶光工坊 · 瑶光星 AI 助手（Alkaid）》原有设计之上，吸收 Claude Code 的架构优点，增强为**带工作流进度可见性与更聪慧的智能体**。  
> 与原文冲突时以本文档的「增强条款」为准；未提及部分沿用原文档。

---

## 1. 增强目标概述

### 1.1 从 Claude Code 借鉴的核心优点

| 优点 | 在瑶光星中的增强形态 |
|------|------------------------|
| **Agentic Loop** | 瑶光星不再只是「一次生成」，而是「多轮决策：选工具 → 执行 → 观察结果 → 再决策」，直到任务完成或用户打断。 |
| **内置工具（Tools）** | 将能力拆成可被模型按需调用的工具（读工作流、校验、修补、试跑、查能力等），模型在会话中自主选择调用顺序。 |
| **工作流进度可见** | 用户可看到当前处于「规划 / 生成 / 校验 / 修复 / 试跑」的哪一阶段、正在调用哪个工具、执行到第几步，而不是黑盒等待。 |
| **多轮对话与记忆** | 支持连续多轮对话、简要会话记忆与当前工作流状态上下文，用户可随时补充需求或纠正方向。 |
| **人类在环（Human in the Loop）** | 对「写回画布」「应用补丁」等写操作默认需用户确认；用户可随时打断并给出新指令。 |
| **可插拔的 Hooks** | 在关键节点（生成前/后、导入前、运行失败时）提供可配置的钩子，用于合规、风控或策略注入。 |
| **子代理（可选）** | 将「诊断」「修图」等专项任务交给独立子代理，主代理负责编排与汇总，降低单次上下文压力并提升效果。 |

### 1.2 增强后的瑶光星定位

- **原定位**：将自然语言目标转换为可导入、可执行的工作流 JSON。  
- **增强后**：在工作流编辑器中提供**全能小机器人**——既能生成/修复工作流，又能**可见地**执行多步推理与工具调用，并展示**工作流进度**（当前阶段、正在执行的工具、执行结果摘要），使用户感知「它在做什么、做到哪了」。

## 2. 工作流进度（可见性与状态）

### 2.1 为何需要「工作流进度」

- 用户需要知道：瑶光星当前在「想」还是在「做」、做的是哪一步、有没有卡住或失败。  
- 与 Claude Code 的「工具调用即执行」一致：每次工具调用都是一步可展示的进度。  
- 便于打断、重试与审计（例如：校验失败后用户可看到是「校验」这一步报错，并选择重试或改需求）。

### 2.2 进度模型（Agent 执行阶段 + 工具步）

#### 2.2.1 阶段（Phase）——高层进度

建议在前端与后端统一使用以下阶段枚举，并随 Agent 执行推进而更新：

| 阶段 | 说明 | 典型展示文案（示例） |
|------|------|----------------------|
| `idle` | 等待用户输入 | 等待您的需求 |
| `planning` | 理解需求、选择模板或规划节点 | 正在理解需求并规划工作流 |
| `generating` | 调用生成工具，产出工作流 JSON | 正在生成工作流 |
| `validating` | 调用校验工具 | 正在校验工作流结构 |
| `repairing` | 根据校验/运行错误进行修复 | 正在根据错误修复工作流 |
| `running_trial` | 试跑工作流（可选） | 正在试跑工作流 |
| `summarizing` | 生成对用户的总结或建议 | 正在总结结果 |
| `waiting_approval` | 等待用户确认（应用修改 / 应用补丁） | 请确认是否应用到画布 |
| `error` | 某步失败且未自动恢复 | 步骤失败，可重试或修改需求 |

#### 2.2.2 工具步（Tool Step）——细粒度进度

每次模型发起一次工具调用，即产生一条**工具步**记录，建议结构：

```ts
interface AgentToolStep {
  stepId: string;           // 唯一标识
  phase: Phase;             // 所属阶段
  toolName: string;         // 如 get_workflow, validate_workflow, patch_workflow
  toolInput: Record<string, unknown>;  // 调用参数（可脱敏展示）
  status: 'pending' | 'running' | 'success' | 'error';
  startedAt: string;        // ISO8601
  finishedAt?: string;
  resultSummary?: string;   // 给用户看的简短结果，如 "校验通过" / "发现 2 处错误"
  errorMessage?: string;    // 若 status === 'error'
}
```

- **工作流进度** = 当前 **Phase** + 当前/最近若干条 **AgentToolStep** 的列表。  
- 前端可展示：当前阶段 + 步骤列表（进行中高亮、失败标红、成功打勾），并可展开某步看 `resultSummary` 或错误详情。

### 2.3 进度推送与前端展示

- **后端**：在 Agent Loop 中，每开始/结束一个阶段或一个工具步，通过 **SSE 或 WebSocket** 推送进度事件（如 `phase_changed`、`tool_step_started`、`tool_step_finished`）。  
- **前端**：  
  - 在瑶光星面板顶部或侧边展示**当前阶段**与**最近 N 条工具步**（如 5～10 条）。  
  - 支持「仅展示阶段」的简洁模式与「展示阶段+工具步」的详细模式。  
  - 若某步失败，在对应步骤旁提供「重试」「跳过」（若业务允许）或「结束并反馈」等操作。

### 2.4 与「工作流执行进度」的区分

- **本文的「工作流进度」**：指**瑶光星 Agent 自身的执行进度**（规划→生成→校验→修复→试跑等）。  
- **工作流运行进度**：指用户点击「运行」后，引擎执行各节点的进度（如 node-1 完成、node-2 执行中）。  
- 两者可分别展示：  
  - 瑶光星面板内：展示 Agent 阶段 + 工具步；  
  - 画布或运行面板：展示工作流执行进度（沿用现有设计）。  
- 当瑶光星调用 `run_workflow_trial` 时，可将试跑产生的**工作流执行进度**作为该工具步的 `resultSummary` 或详情的一部分展示，使用户在「小机器人进度」里也能看到「试跑到哪了」。

## 3. 更聪慧的智能体：Agentic Loop 与内置工具

### 3.1 从「单次生成流水线」升级为「Agentic Loop」

- **原形态**：用户输入 → 规划 → 生成 → 校验 → 修复（固定顺序，单次或有限次）。  
- **增强形态**：  
  - 用户输入与历史消息 + 当前**工作流状态**（若有）作为上下文；  
  - 模型每轮可**选择**：回复用户 或 调用若干**工具**；  
  - 工具执行结果返回模型，模型再决定：继续调工具、或回复用户并结束本轮。  
  - 循环直到模型输出「最终回复」且不再调用工具，或达到最大步数/超时，或用户打断。

这样，瑶光星可以「先校验再生成」「先试跑再修」「根据错误多次修复」，行为更智能且可观测。

### 3.2 内置工具清单（Tools）

以下工具为瑶光星智能体在会话中可调用的**内置工具**，需在后端实现并在模型侧注册为 function/tool 定义。

#### 3.2.1 只读类

| 工具名 | 说明 | 典型参数 | 返回（摘要） |
|--------|------|----------|--------------|
| `get_capabilities` | 获取节点类型、默认配置、IO、约束等（Capabilities） | 无或 `capabilitiesVersion` | 当前能力说明（可用于生成与校验的权威依据） |
| `get_workflow` | 获取当前画布上的工作流 JSON（若存在） | 无 | 当前工作流 JSON 或「无」 |
| `get_node_spec` | 查询某类节点的规格（配置项、IO、示例） | `nodeType: string` | 该类型的 spec 片段 |

#### 3.2.2 校验与执行类

| 工具名 | 说明 | 典型参数 | 返回（摘要） |
|--------|------|----------|--------------|
| `validate_workflow` | 校验工作流结构与规则 | `workflow: WorkflowExportData` | `{ valid: boolean, errors: ValidationError[] }` |
| `run_workflow_trial` | 试跑工作流（沙箱/真实，按策略） | `workflow: WorkflowExportData`, 可选 `timeout` | 成功则摘要；失败则 `ExecutionError`（含 failedNodeId、errorCode、message、details） |

#### 3.2.3 写操作类（需人类确认）

| 工具名 | 说明 | 典型参数 | 返回与约束 |
|--------|------|----------|------------|
| `propose_workflow` | 提出一份完整工作流，供用户「应用到画布」 | `workflow: WorkflowExportData`, 可选 `explanation` | 返回「已记录，等待用户确认」；不直接写画布 |
| `propose_patch` | 提出对当前画布的补丁（若干节点的修改） | `patch: PatchItem[]`, 可选 `reason` | 同上，等待用户确认后再应用 |

- 所有「写」类工具均不自动写回画布；前端展示 diff 或变更说明，用户点击「应用」后再调用现有的 `importWorkflow` / 应用 patch 接口。  
- 可选：在设置中提供「自动应用安全变更」开关（仅限非敏感字段），默认关闭。

### 3.3 工具与进度的对应关系

- 每调用一次工具，即产生一条 **AgentToolStep**，并更新当前 **Phase**（如调用 `validate_workflow` 时 phase 为 `validating`）。  
- 前端根据 Phase + ToolStep 列表渲染「工作流进度」，使用户清楚看到「小机器人」正在执行哪一步。

### 3.4 会话与上下文

- **会话**：一次打开瑶光星面板到关闭，或一次「新对话」到「结束对话」，为一个会话。  
- **上下文**：  
  - 当前会话的多轮消息（user / assistant / tool 结果）；  
  - 当前会话中若已存在「待确认的 workflow 或 patch」，也应作为上下文的一部分（如用 `get_workflow` 可读到的「当前提议」）；  
  - 可选：简要会话记忆（如「用户希望避免使用爬虫」「用户偏好 deepseek」）在实现成本允许时可加入。  
- **长度与截断**：对历史消息与工具结果做长度或条数限制，超出时摘要或丢弃最旧部分，避免超出模型上下文窗口。

## 4. 人类在环（Human in the Loop）

### 4.1 需确认的操作

- **应用工作流**：模型通过 `propose_workflow` 产出工作流后，前端展示摘要（节点数、边、关键节点类型）及「应用」「放弃」；用户点击「应用」才写入画布。  
- **应用补丁**：模型通过 `propose_patch` 产出补丁后，前端展示 diff（改了哪些 node、哪些字段、原因简述）；用户确认后再调用应用 patch 接口。  
- **试跑**：若试跑会访问外部资源或产生副作用，建议首次询问用户是否允许试跑；若仅限本地/沙箱则可降低确认级别（按安全策略配置）。

### 4.2 用户打断

- 用户在 Agent 执行过程中（如多步工具调用未结束前）可输入新消息并发送，视为**打断**。  
- 后端行为：结束当前 Agent 轮次（不再执行后续排队工具），将用户新输入作为下一轮 user message，继续 Agent Loop。  
- 前端：在进度区标注「已由用户打断」，并可保留已执行的步骤历史供参考。

## 5. Hooks（可插拔钩子）

### 5.1 事件与用途

在以下时机触发 Hooks，便于做合规、风控或策略注入（不改变主流程语义，仅增加侧效应或拦截）：

| 事件 | 时机 | 建议用途 |
|------|------|----------|
| `BeforeGenerate` | 模型即将调用生成类逻辑（或首次调用 `propose_workflow`）前 | 检查用户输入是否合规、是否包含敏感词、是否强制使用某模板 |
| `AfterGenerate` | 已得到一份工作流草案（未写画布） | 日志、审计、或对 JSON 做一次内部复核 |
| `BeforeApplyWorkflow` | 用户点击「应用」、即将写入画布前 | 再次校验、限制节点数量/类型、禁止写入敏感配置 |
| `OnWorkflowRunFailed` | 工作流执行失败（含试跑） | 触发「小精灵」诊断、或自动调用 `suggest_patch` 的入口 |

### 5.2 接口形态（建议）

- 每个 Hook 为可配置的**脚本或 HTTP 回调**（与 Claude Code 的 command/prompt hooks 思路类似）。  
- 入参：`event`、`sessionId`、`payload`（如当前 workflow、错误信息、用户输入摘要）。  
- 返回：  
  - **允许继续**：正常返回；  
  - **拒绝**：返回 `{ allow: false, reason: string }`，前端展示 `reason`，不执行写画布或不再继续该轮生成。  
- 若 Hook 执行超时或异常，建议默认「允许继续」，并打日志，避免阻塞用户。

## 6. 子代理（可选增强）

### 6.1 何时引入

- 当单轮上下文压力大（工具结果很多、历史很长）或希望「诊断」与「修图」逻辑更专注时，可引入子代理。  
- 主代理负责：理解用户、选择工具、决定何时调用子代理、汇总结果。  
- 子代理示例：  
  - **诊断子代理**：输入为 ExecutionError + 工作流片段；输出为结构化诊断（原因、建议、可能补丁方向）。  
  - **修图子代理**：输入为工作流 + 校验错误或执行错误；输出为 `propose_patch` 所需的 patch 列表。  

### 6.2 与进度的关系

- 调用子代理时，可在进度中增加 **Phase** 如 `diagnosing` / `repairing`，并增加一条「子代理调用」类型的步骤（不暴露子代理内部多步也可），使用户知道当前在「诊断」或「修复」阶段。

## 7. 与原有文档的对接点

### 7.1 保留并强化的内容

- **Capabilities / NodeSpec**：仍为生成与校验的权威来源；通过 `get_capabilities` / `get_node_spec` 暴露给智能体。  
- **WorkflowExportData、节点/边结构、变量模板语法**：不变；工具的参数与返回值与之对齐。  
- **校验与修复**：`validate_workflow`、`validate_workflow` 的 errors 驱动 `repair_workflow` 或 `propose_patch`；原有 5.4、5.5、8.2、8.3、8.4 的接口与逻辑可复用为工具的底层实现。  
- **安全与合规**：原 9 节保留；Hooks 在此基础上增加 BeforeApply、BeforeGenerate 等检查点。  
- **国际化**：原 10 节保留；新增进度与智能体相关文案使用 `workflowEditor.alkaid.*` 前缀，如 `workflowEditor.alkaid.phase.validating`、`workflowEditor.alkaid.toolStep.success`。

### 7.2 新增或变更的接口（建议）

- **进度推送**：`GET /api/alkaid/session/{sessionId}/stream` 或 WebSocket，在流式返回 assistant 内容的同时推送 `phase`、`tool_step` 事件。  
- **工具执行**：由后端 Agent Loop 在内部调用现有 `validate`、`repair`、`run_trial`、`suggest-patch` 等接口，不对前端直接暴露「工具 URL」；前端只消费进度与最终 assistant 回复。  
- **确认写回**：`POST /api/alkaid/apply-workflow`、`POST /api/alkaid/apply-patch`，由前端在用户确认后调用，与现有导入/应用 patch 逻辑统一。

## 8. 验收标准（增强部分）

在原有 11 节验收标准基础上，增加：

1. **工作流进度**：Agent 执行过程中，前端能展示当前阶段（Phase）及至少最近 5 条工具步，且步骤状态（pending/running/success/error）与后端一致。  
2. **Agentic Loop**：用户输入一次需求后，瑶光星可自动完成多步（如生成 → 校验 → 修复 → 再校验），无需用户每步点击；且用户可在中途打断并输入新需求。  
3. **人类在环**：生成的 workfow 或 patch 需经用户确认后才写入画布；确认前有清晰 diff 或变更说明。  
4. **内置工具**：至少实现 `get_capabilities`、`get_workflow`、`validate_workflow`、`propose_workflow` 并在会话中被模型按需调用；工具调用与进度展示联动。  
5. **Hooks（可选）**：至少实现 `BeforeApplyWorkflow` 或 `OnWorkflowRunFailed` 之一，并能在配置开启时生效（如拒绝应用或触发诊断）。

## 9. 附录：进度与工具步的示例 Payload（SSE）

```json
{ "event": "phase_changed", "phase": "validating", "at": "2026-02-09T12:00:00.000Z" }
{ "event": "tool_step_started", "stepId": "step-3", "toolName": "validate_workflow", "phase": "validating", "at": "2026-02-09T12:00:01.000Z" }
{ "event": "tool_step_finished", "stepId": "step-3", "status": "success", "resultSummary": "校验通过，共 6 个节点", "at": "2026-02-09T12:00:02.000Z" }
```

前端可根据 `event` 更新 Phase 与 ToolStep 列表，并刷新进度 UI。
