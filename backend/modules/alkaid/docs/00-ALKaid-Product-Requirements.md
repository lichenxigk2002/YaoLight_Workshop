## 1. 产品背景

瑶光工坊本质上是一个工作流平台。

用户的真实问题不是“没有聊天助手”，而是：

- 不会搭工作流
- 不知道节点怎么选
- 不知道变量怎么传
- 工作流跑不通时不会排查
- 已有工作流想改，但不知道从哪里下手

瑶光星的目标，不是成为通用 Agent，而是成为这个平台里的**工作流助手**。

---

## 2. 产品定位

瑶光星的定位是：

**YaoLight 平台内的 Workflow Copilot**

它不追求解决开放世界问题，只聚焦平台内的工作流任务。

### 2.1 目标用户

1. 不会搭工作流的新手用户
2. 会搭基本流程，但不熟悉节点细节的普通用户
3. 已有流程，但想快速修改、优化、排错的中级用户

### 2.2 产品目标

瑶光星要帮助用户完成四件事：

1. 生成新工作流
2. 理解当前工作流
3. 修复或优化当前工作流
4. 试跑并定位失败原因

### 2.3 不做什么

瑶光星不做：

- 通用代码智能体
- 任意领域开放式任务代理
- 长时间无人监管的自主执行 Agent
- 与 Claude Code、Codex、Cursor 一类产品正面对标

---

## 3. 核心价值

瑶光星的价值不是“像真人聊天”，而是：

- **懂画布**
- **懂节点**
- **懂变量**
- **懂执行约束**
- **会校验**
- **会修补**
- **能交付可应用结果**

对用户来说，最重要的不是它会说多少，而是：

- 能不能生成一条能跑的流程
- 能不能把现有坏流程修好
- 能不能告诉我为什么报错
- 能不能把结果以可应用方式交给我

---

## 4. 产品边界

### 4.1 核心任务模式

新版瑶光星收敛为五种任务模式：

| 模式 | 用户目标 | 是否改画布 | 是否试跑 | 主结果 |
|------|----------|------------|----------|--------|
| `chat` | 基础问答 | 否 | 否 | 文本答复 |
| `explain` | 解释当前工作流 | 否 | 否 | explanation report |
| `generate` | 新建工作流 | 是 | 是 | pending workflow |
| `repair` | 修复/优化工作流 | 是 | 是 | pending patch / workflow |
| `trial_debug` | 试跑并定位失败 | 否或有限 | 是 | debug report |

### 4.2 模式说明

#### `chat`

用于：

- 平台使用说明
- 节点概念说明
- 普通咨询

不用于：

- 直接生成流程
- 修改当前画布

#### `explain`

用于：

- 解释当前工作流结构
- 说明节点作用和变量流转
- 指出潜在风险

不用于：

- 自动生成 patch

#### `generate`

用于：

- 基于用户目标新建流程

要求：

- 默认走校验
- 在可控范围内试跑
- 最终生成 `pendingWorkflow`

#### `repair`

用于：

- 修改、修复、优化已有工作流

要求：

- 能定位问题
- 能产出 patch 或替代 workflow
- 最终进入待确认状态

#### `trial_debug`

用于：

- 试跑当前流程
- 找出失败节点
- 给出失败说明和下一步建议

默认不直接修改画布。

## 5. 用户体验目标

### 5.1 用户感知重点

瑶光星的“智能感”主要来自：

1. 能正确理解当前任务属于哪一类
2. 能告诉用户现在在做什么
3. 能展示关键检查过程
4. 能把结果作为可应用工件交给用户

### 5.2 不希望出现的体验

不希望出现：

- 说很多，但没有结果
- 给出大段文字，让用户自己找 JSON
- 明明是看当前工作流，却跑去生成新流程
- 明明是修流程，却只是解释问题不落补丁
- 试跑失败后没有具体节点和原因

### 5.3 期望的交付形式

不同模式的理想交付：

- `chat`：简洁答复
- `explain`：解释报告
- `generate`：待确认工作流
- `repair`：待确认补丁或替代工作流
- `trial_debug`：调试报告

---

## 6. 产品亮点定义

瑶光星的亮点不定义为“最强智能体”，而定义为：

**一个懂 YaoLight 工作流、能把需求落成可运行流程的专用 Copilot。**

亮点具体体现为：

1. 给一句需求，能生成一条大概率能跑的流程
2. 给一条坏流程，能指出问题并给补丁
3. 能主动做校验和试跑，而不是只给草稿
4. 能把结果以 `pending workflow / pending patch / debug report` 的方式交付

---

## 7. 成功标准

如果瑶光星满足以下条件，就算产品方向成立：

### 7.1 生成能力

- 用户一句自然语言能得到一条结构清晰的工作流
- 工作流默认能通过基础校验
- 在支持场景下能完成试跑

### 7.2 修复能力

- 用户提供现有工作流后，瑶光星能指出关键问题
- 至少能生成补丁或替代流程
- 修改结果可解释

### 7.3 调试能力

- 试跑失败时，能指出失败节点
- 能给出具体错误原因或高概率原因
- 能给出下一步建议

### 7.4 交互体验

- 用户能感知当前任务模式
- 用户能感知当前阶段
- 用户看到的是可应用结果，而不是原始中间输出

---

## 8. 版本范围

### 8.1 第一阶段必须做

1. 任务模式收敛
2. 待确认工作流/补丁交付
3. 校验与试跑闭环
4. 当前工作流解释能力
5. 调试报告输出

### 8.2 第一阶段不做

1. 通用工具代理
2. 子代理系统
3. 超长链路自主规划
4. 与代码仓库直接协同的开放式 Agent
