## 1. 背景

当前项目已经具备以下能力：

- 用户可在前端编排工作流
- 后端可执行工作流，并生成 `task`
- 输出节点可把结果落为 `artifact`
- 用户可通过站内 JWT 接口查看任务、查看 artifact、下载 artifact

这说明“工作流执行”和“结果导出”能力已经存在，但它仍是**站内能力**，不是“可交付给外部人员直接调用的 API 产品”。

用户当前的真实诉求不是单纯“输出节点多一个导出选项”，而是：

- 把某个工作流发布成一个稳定接口
- 生成可交付的 API 地址
- 生成和管理 API Key
- 自动生成给外部人员查看的接入文档
- 让外部人员在不登录站内系统的情况下调用
- 按约定拿到 JSON 结果或导出文件

---

## 2. 当前现状结论

## 2.1 已有能力

- `POST /api/workflows/execute` / `POST /api/workflows/execute/stream` 可执行工作流
- 执行时会创建 `task`
- 输出节点会生成 `artifact`
- 当前已有：
  - `GET /api/tasks/:id/artifacts`
  - `GET /api/artifacts/:id`
  - `GET /api/artifacts/:id/download`

## 2.2 当前缺口

- 上述接口都依赖站内用户 JWT，外部人员无法直接调用
- 当前 `destination=api` 更接近“内部可通过任务产物接口检索”，并不等于真正的“对外 API 发布”
- 开始节点当前只有静态 `inputData`，没有标准的“运行时请求入参”注入能力
- 没有 API Key 管理、调用日志、限流、停用、示例代码等能力

## 2.3 核心判断

本需求**能做**，而且适合基于现有 `workflow -> task -> artifact` 链路扩展。

但产品设计上不建议继续把“API 地址、密钥、对外调用规则”写在输出节点里。  
输出节点只负责定义“导出什么结果”，真正的开放能力应放在**工作流发布层**。

---

## 3. 产品定位

本能力定位为：

> 将工作流发布为可被外部系统调用的 API，并基于 API Key 进行鉴权、调用、结果查询与产物下载。

一句话区分职责：

- 工作流：定义处理逻辑
- 输出节点：定义输出结果和导出物
- API 发布：定义谁可以调、怎么调、返回什么、如何追踪

---

## 4. 产品目标

## 4.1 目标

- 用户可将一个工作流发布为外部 API
- 系统生成稳定的 API 地址和可管理的 API Key
- 系统为每个已发布工作流自动生成一份接入文档
- 外部调用方可提交入参并触发工作流执行
- 系统支持返回 JSON、artifact，或两者混合
- 用户可查看调用记录、状态、错误与下载记录

## 4.2 业务收益

- 把“低代码工作流”从站内工具升级为可集成能力
- 让客户、合作方、外包、内部其他系统都能消费工作流结果
- 提升工作流复用率与商业化交付能力
- 让输出节点导出的文档、图表、文件真正可对外交付

---

## 5. 非目标

本期明确不做：

- 面向全站公开的匿名 API
- 通用 API 网关平台
- 多租户复杂计费结算
- OpenAPI 自动代码生成的完整平台化能力
- 复杂审批流
- 外部调用方账号体系

---

## 6. 角色与场景

## 6.1 角色

- 工作流拥有者：创建、发布、停用 API
- 外部调用方：持有 API 地址和 Key，调用接口
- 管理员：查看异常调用、滥用、封禁、审计

## 6.2 典型场景

### 场景 A：文本 / JSON 处理 API

外部人员提交一段文本或结构化 JSON，工作流经过 AI / 清洗 / 判断后返回 JSON 结果。

### 场景 B：文档导出 API

外部人员提交参数，工作流生成 `pdf/docx/markdown/json`，输出节点产出 artifact，外部人员下载文件。

### 场景 C：图表导出 API

外部人员提交业务数据，工作流生成 `chart/svg/png/mermaid`，对方通过接口获取图表文件。

---

## 7. 核心产品决策

## 7.1 API 发布是“工作流级”能力

发布入口应放在工作流页面，而不是输出节点配置里。

原因：

- 一个工作流可能有多个输出节点
- 一个工作流可能被发布成多个不同用途的 API
- API Key、限流、日志、状态不属于节点职责
- 输出节点负责“产物”，发布层负责“开放”

## 7.2 输出节点仍然保留 API 相关语义，但不承载发布职责

输出节点中的 `destination=api` 可保留为“该输出适合外部交付”的提示或结果模式依据，但它不再等价于“已经对外发布”。

## 7.3 MVP 先支持 API Key 模式

本期只支持：

- `X-API-Key`
- 单 Key 调用
- 手动创建 / 禁用 / 轮换

暂不支持 OAuth、签名验签等复杂模式。

---

## 8. MVP 范围

## 8.1 发布管理

- 在工作流详情页新增“发布为 API”
- 可配置：
  - API 名称
  - 路径别名 `slug`
  - 描述
  - 状态：草稿 / 已发布 / 已停用
  - 返回模式：`json` / `artifact` / `mixed`
  - 执行模式：`async` / `wait`
  - 等待超时秒数
  - 允许外部下载 artifact

## 8.2 API Key 管理

- 创建 Key
- 仅首次展示明文
- 查看前缀、名称、创建时间、最后使用时间
- 禁用 Key
- 轮换 Key

## 8.3 运行时入参

- 外部请求 body 可作为工作流运行时输入
- MVP 默认注入到开始节点
- 工作流内可通过变量引用运行时数据
- 支持保存请求示例 JSON，便于文档展示

## 8.4 外部调用

- 外部持 Key 调用已发布工作流
- 支持两种模式：
  - `async`：立即返回 `requestId`，外部轮询结果
  - `wait`：在超时内等待执行完成，完成则直接返回结果，否则返回 `requestId`

## 8.5 结果返回

- `json`：返回工作流结果 JSON
- `artifact`：返回 artifact 列表与下载地址
- `mixed`：同时返回 JSON 与 artifact 列表

## 8.6 调用记录

- 查看最近调用记录
- 查看请求时间、状态、耗时、来源 IP、错误信息
- 查看关联任务和产物

## 8.7 接入文档页

- 每个已发布 API 自动生成一页接入文档
- 文档页风格目标参考 Dify 的“API Access”体验
- 至少包含：
  - API 名称与说明
  - Base URL
  - 路径与请求方法
  - 鉴权方式
  - 请求 body 示例
  - 返回结果示例
  - 错误码说明
  - `curl` 示例
  - `JavaScript` 示例
  - `Python` 示例
  - `async / wait` 调用差异说明
  - artifact 下载说明
  - requestId 轮询说明

## 9. 详细功能要求

## 9.1 发布页

页面应展示：

- API 基本信息
- 当前发布状态
- 可调用地址
- 接入文档地址
- 示例请求头
- 示例 cURL
- 请求示例 JSON
- 返回示例
- Key 列表
- 最近调用记录

## 9.2 Key 行为

- Key 明文只在创建成功时展示一次
- 后端只保存哈希，不保存可逆明文
- Key 可设置失效时间
- 被禁用或过期的 Key 不可调用

## 9.3 调用规则

请求头：

```text
X-API-Key: ylw_live_xxx
Content-Type: application/json
```

请求体建议结构：

```json
{
  "input": {
    "title": "示例标题",
    "content": "示例内容"
  },
  "options": {
    "responseMode": "wait"
  }
}
```

## 9.4 结果规则

### `async`

返回：

- `requestId`
- `status`
- `resultQueryUrl`

### `wait`

若超时前完成：

- 直接返回最终结果

若超时前未完成：

- 返回 `requestId`
- 外部再轮询查询

## 9.5 文件下载

若工作流生成 artifact，则外部应通过开放接口下载，不要求站内 JWT。

## 9.6 限流与安全

MVP 必须支持：

- 每个发布 API 配置基础限流
- 审计调用 IP 与 User-Agent
- 可停用某个发布 API
- 可停用某个 Key

MVP 可选支持：

- IP 白名单

## 9.7 接入文档要求

接入文档不是后台说明文档，而是**给外部开发者直接使用的产品文档页**。

文档页应满足：

- 非站内编辑态也可访问
- 可复制 API 地址
- 可复制 Key 使用方式
- 可直接切换 `curl / JS / Python`
- 可展示示例请求与示例响应
- 若工作流返回 artifact，明确说明“先调用、再查询、再下载”的链路

文档页建议支持两种访问方式：

- 工作流拥有者在站内查看完整文档
- 外部接入方通过分享链接查看只读文档

## 10. 信息架构与入口建议

建议在用户侧工作流相关页面新增：

- 工作流详情页按钮：`发布为 API`
- 工作流 API 管理页：`/workflows/:id/api`

页面建议分区：

- 概览
- 接口配置
- 密钥管理
- 调用示例
- 调用记录

管理员侧可在后续补：

- API 发布总览
- 异常调用审计
- Key 滥用排查

---

## 11. 成功标准

MVP 上线后，至少满足：

- 用户能在 5 分钟内完成一次工作流 API 发布
- 外部人员只凭 API 地址和 Key 即可完成调用
- 至少支持一个 JSON 返回场景和一个 artifact 下载场景
- 用户可定位失败调用的原因

---

## 12. 风险与注意点

- 当前执行链路强依赖 `task`，不能绕开任务直接做“纯函数式 API”
- 当前开始节点是静态输入，必须补运行时入参注入
- 当前 `destination=api` 容易让用户误以为已经“对外开放”，文案需重新定义
- artifact 下载若直接暴露站内接口，会与 JWT 模式冲突，必须补开放下载链路

---

## 13. 分阶段建议

## 阶段 1：MVP

- 工作流发布
- API Key
- 自动生成接入文档页
- async / wait 调用
- JSON / artifact 返回
- 调用记录

## 阶段 2：增强

- 多版本发布
- 请求参数校验 schema
- IP 白名单
- 更完整的调用文档页
- Webhook 回调

## 阶段 3：平台化

- 调用配额与计费
- 更细粒度权限
- API 市场 / 对外集成中心

---

## 14. 最终结论

这个能力不应该继续“写在输出节点里”。

正确的产品边界应该是：

- 输出节点负责结果和产物
- 工作流发布层负责 API 地址、Key、调用协议、审计和安全

在当前项目基础上，这个方案是可落地的，而且复用现有 `task` 与 `artifact` 体系成本最低。
