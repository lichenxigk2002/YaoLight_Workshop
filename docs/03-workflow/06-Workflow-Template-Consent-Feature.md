# 工作流模板发布：源作者确认功能设计

## 一、需求简述

发布基于「源工作流」的模板时，源工作流属于用户私有数据。希望增加**站内消息确认**流程：

1. 管理员将某模板设为「发布」且该模板绑定了源工作流时，先不直接发布；
2. 系统向**源工作流作者**发送一条站内消息，说明：认为其工作流优秀，希望作为平台模板使用，请确认是否同意；
3. 用户可在站内消息中操作：**同意** 或 **拒绝**；
4. **同意**：该模板可正常发布/使用；**拒绝**：该模板不可发布（或保持草稿/待确认状态，不可对外使用）。

---

## 二、合理性

- **合规与隐私**：源工作流是用户私有资产，未征得同意就作为公开模板使用存在合规与体验风险。
- **尊重作者**：明确告知并征得同意，能提升作者对平台的信任和参与意愿。
- **与现有能力一致**：已有站内通知（创建、推送、列表、已读）和 WebSocket 实时推送，本功能是在此基础上的业务扩展，复用通知通道与前端入口即可。
- **实现成本可控**：后端增加「模板-源作者同意」状态与一条用户端「对通知进行同意/拒绝」的 API，前端在通知详情/列表中为该类消息增加「同意」「拒绝」按钮即可。

结论：**该需求合理，且与现有架构匹配，适合做成「发布前站内确认」流程。**

---

## 三、实现思路

### 3.1 流程概览

```
[管理员] 将模板状态改为「已发布」且模板有 source_workflow_id
    → [后端] 检查是否已有该「模板+源工作流」的作者同意记录
        → 已同意：直接更新模板为 published
        → 未同意：不更新为 published，并给源工作流作者发一条「模板征用确认」站内消息，写入一条「待确认」同意记录
    → [用户] 在站内消息中看到「您的某工作流被选为模板候选…」，可点「同意」或「拒绝」
    → [用户端 API] 调用「对通知进行同意/拒绝」接口
    → [后端] 更新同意记录为 agreed / rejected
        → 同意：允许该模板之后可被发布（管理员再次点发布即可成功，或可选自动发布）
        → 拒绝：不创建/不更新为同意，模板保持不可发布
```

### 3.2 后端

1. **同意记录表**（新建，例如 `workflow_template_consents`）  
   - 字段建议：`id`, `template_id`, `source_workflow_id`, `source_owner_user_id`, `status`（`pending` / `agreed` / `rejected`）, `notification_id`（可选，关联发出的那条站内消息）, `created_at`, `responded_at`。  
   - 用于：判断「该模板+该源工作流」是否已征得作者同意、以及是待确认/同意/拒绝。

2. **管理员「发布」模板时的逻辑**（在现有 UpdateTemplate 或发布接口中）  
   - 当请求将模板状态更新为 `published` 且模板存在 `parent_id`（即 source_workflow_id）时：  
     - 查询源工作流，得到 `user_id`（源作者）；  
     - 查同意表：是否存在 `template_id` + `source_workflow_id` 且 `status = agreed`；  
       - 若已同意：正常将模板置为 `published`；  
       - 若存在 `pending`：可返回明确提示「已发送确认请求，请等待作者同意」；  
       - 若不存在或为 `rejected`：可先查是否已有对应 `pending` 通知，若无则创建一条站内消息（见下），并写入一条 `pending` 同意记录，然后返回「已向源工作流作者发送确认请求，待其同意后可再次发布」之类提示，**不**将模板设为 `published`。

3. **站内消息**  
   - 类型：例如 `workflow_template_consent_request`。  
   - 接收人：源工作流的 `user_id`。  
   - 标题/正文：如「您的工作流《xxx》被选为平台模板候选，是否同意作为公开模板使用？」（可带模板名称、管理员/平台名称等）。  
   - `related_resource_type` / `related_resource_id` 或 `metadata`：可带 `template_id`、`source_workflow_id`、`consent_id` 等，便于前端展示和调用「同意/拒绝」接口。

4. **用户端「对通知进行同意/拒绝」接口**  
   - 例如：`POST /api/notifications/:id/consent`，body：`{ "action": "agree" | "reject" }`。  
   - 校验：仅通知的接收人（当前登录用户）可操作；且通知类型为 `workflow_template_consent_request`；可选：仅 `pending` 的同意记录可被更新。  
   - 逻辑：根据 `notification_id` 或 metadata 找到对应的 `workflow_template_consent` 记录，将 `status` 更新为 `agreed` 或 `rejected`，并更新 `responded_at`；可选：同意时顺带将对应模板状态改为 `published`（若产品希望「用户同意即自动发布」）。

5. **模板「是否可用」的判定**  
   - 对外展示/使用模板时：若模板有 `parent_id`，可要求存在对应同意记录且 `status = agreed`，否则视为未授权，不可被使用或不可显示为已发布。

### 3.3 前端（用户端 frontend）

1. **站内消息列表/详情**  
   - 对类型为 `workflow_template_consent_request` 的通知，展示友好文案（标题+正文），并展示两个操作按钮：「同意」「拒绝」。

2. **点击「同意」/「拒绝」**  
   - 调用 `POST /api/notifications/:id/consent`，传 `action: "agree"` 或 `"reject"`；  
   - 成功后：可刷新通知列表、标记该条已读、并 toast 提示「已同意」或「已拒绝」。

3. **（可选）管理端 admin-frontend**  
   - 在模板列表/详情中，若模板存在源工作流且同意状态为 `pending`，可展示「等待源作者确认」；若为 `rejected`，可展示「源作者已拒绝」，并禁止发布或提示需更换源工作流。

### 3.4 数据与兼容

- 仅当模板**有** `source_workflow_id`（parent_id）时走上述流程；无源工作流的模板仍可直接发布，无需改动现有逻辑。
- 历史已发布模板：若当时无同意表，可按「无 parent_id 或已有 published 状态即视为历史兼容」处理，或为历史数据补一条「同意」记录（按需）。

---

## 四、小结

| 项目     | 说明 |
|----------|------|
| 合理性   | 源工作流属用户私有，发布前征得同意合规且提升体验，与现有通知能力契合。 |
| 触发时机 | 管理员将「有源工作流」的模板设为「已发布」时，先查同意记录再决定是否发布或发站内消息。 |
| 用户操作 | 源作者在站内消息中点击「同意」或「拒绝」，调用用户端 API 更新同意状态。 |
| 结果     | 同意后该模板可发布/使用；拒绝后不可发布或不可使用，管理员可更换源或保持草稿。 |

按上述思路即可实现「发布前站内消息询问 → 用户同意/拒绝 → 同意则可发布」的完整闭环；若你确认采用，可再细化接口字段与前端交互细节（例如是否同意后自动发布、拒绝后是否允许管理员重发请求等）。
