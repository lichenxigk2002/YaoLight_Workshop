# 项目知识 / 网站源 / 生成物 PRD

| 项目 | 说明 |
|------|------|
| 产品名称 | 瑶光工坊 · 项目资产中心 |
| 文档版本 | 1.0 |
| 适用系统 | frontend、backend、admin-frontend |
| 文档目标 | 统一定义面向用户的项目知识、网站源、生成物三类资产能力，并明确与 Alkaid、工作流、任务体系的衔接方式 |

---

## 1. 背景

当前系统已经具备以下基础能力：

- Alkaid 可检索系统知识并辅助生成工作流
- 输出节点可将结果落为 `artifact`
- 用户已能在执行结果和任务详情中查看、下载部分生成物
- 管理端已有系统级知识库管理能力

但从用户主流程看，仍有三个缺口：

1. 用户缺少项目内的知识沉淀位置
2. 用户缺少结构化维护“可直接访问的网站源”的位置
3. 用户缺少跨任务、跨工作流、跨时间的生成物归档与复用入口

这会带来几个直接问题：

- Alkaid 对项目背景、站点偏好、抓取约束记忆弱
- 网址虽然能在对话中临时提及，但难以沉淀为长期可复用资产
- 生成物虽然存在，但停留在“某次执行结果附属信息”层，而不是“项目成果资产”

---

## 2. 产品定位

本模块建议统一定位为：

> 项目资产中心，用于沉淀项目级规则知识、可执行网站源，以及工作流生成成果，并让 Alkaid 在项目上下文中使用这些资产。

其中三类资产分别是：

### 2.1 项目知识

用于存放规则、术语、经验、排错建议、输出约定等内容。

它回答的是：

- 这个项目有哪些业务规则
- 这个项目里有哪些常见坑
- Alkaid 在生成和诊断工作流时应参考什么

### 2.2 网站源

用于存放用户可直接访问、可被 crawler 工作流使用的网站信息。

它回答的是：

- 这个项目有哪些可用数据源
- 哪些 URL 是列表页、详情页、入口页
- 这些站点抓取时有哪些注意事项
- Alkaid 在生成 crawler 节点时优先使用哪些源

### 2.3 生成物

用于沉淀工作流执行后的文件、图表、文档、文本等成果。

它回答的是：

- 这个项目已经产出了什么
- 哪些结果可以预览、下载、复发邮件、再次引用
- 某个生成物来自哪个工作流、哪次任务、哪个输出节点

---

## 3. 核心判断

这三个能力不应被当作三个孤立模块，而应构成一条完整闭环：

1. 用户在项目中沉淀知识
2. 用户在项目中维护网站源
3. Alkaid 使用知识和网站源生成工作流
4. 工作流执行后产出生成物
5. 生成物进入项目资产中心，成为可回看、可分发、可复用的成果

一句话说：

> 知识决定“怎么做”，网站源决定“从哪抓”，生成物沉淀“做出了什么”。

---

## 4. 产品目标

### 4.1 产品目标

- 让 Alkaid 在项目内更懂业务背景和数据源上下文
- 让 crawler 节点生成更稳定、更贴近用户真实可访问网站
- 让输出结果从“单次执行附件”升级为“项目资产”
- 让用户能在项目内持续积累可复用能力，而不是每次从零描述

### 4.2 业务收益

- 提升 Alkaid 生成 crawler 工作流的命中率
- 降低用户重复提供网址、规则、站点说明的成本
- 提升项目复用能力和站点经验沉淀能力
- 提升生成结果的可追溯性、可分享性、可管理性

---

## 5. 非目标

本期明确不做：

- 通用知识平台
- 通用书签网站
- 向量数据库平台化
- 复杂文档切片和 embedding 管理
- 大规模文件内容自动解析平台
- 团队级复杂审批、发布流、审核流
- 面向全站公开的生成物市场

本期重点是：

- 项目域
- 用户主流程
- 与 Alkaid 和工作流强关联

---

## 6. 核心原则

### 6.1 项目域优先

所有资产都优先归属于项目，而不是做成脱离项目的全局中心。

### 6.2 结构化优先

尤其是网站源，不能只把 URL 当普通文本存入知识库，而应以结构化方式维护。

### 6.3 轻量可落地

优先复用现有：

- `alkaid_knowledge`
- `artifacts`
- 任务与工作流体系
- Alkaid 检索与工具调用链路

### 6.4 可验证

用户必须能看到：

- 某次 Alkaid 对话引用了哪些知识或网站源
- 某个生成物来自哪个任务和节点
- 某个网站源是否可访问、是否推荐用于 crawler

## 7. 用户角色与场景

### 7.1 角色

- 项目创建者 / 使用者
- 在项目内通过 Alkaid 生成工作流的普通用户
- 需要反复抓取同类站点、复用生成结果的用户

### 7.2 典型场景

#### 场景 A：沉淀项目规则

用户记录：

- 业务术语
- 输出格式要求
- 节点使用约定
- 常见错误与修复方式

Alkaid 在项目内生成工作流和回答问题时自动参考这些内容。

#### 场景 B：维护可抓取网站源

用户维护：

- 网站名称
- 可访问入口 URL
- 列表页、详情页样例
- 抓取提示、反爬说明、登录要求

Alkaid 在生成 crawler 节点时优先从这些网站源中选择候选 URL 和推荐配置。

#### 场景 C：归档项目生成物

用户执行工作流后：

- 生成文档
- 导出图表
- 产生 Markdown、JSON、PDF、DOCX 等结果

这些结果不只在当次执行中可见，还应在项目里长期留存并可再次下载、分享、回看来源。

## 8. 产品范围

## 8.1 MVP 必做

### 项目知识

- 项目知识列表
- 新建 / 编辑 / 删除
- 启用 / 停用
- 按关键字、分类、标签筛选
- 项目内检索测试
- Alkaid 在项目场景自动使用项目知识
- 对话中展示引用的知识条目

### 网站源

- 项目网站源列表
- 新建 / 编辑 / 删除
- 启用 / 停用
- 维护基础 URL 与示例 URL
- 维护抓取提示、站点说明、标签
- 一键做可访问性校验
- Alkaid 在生成 crawler 节点时可自动参考网站源
- 对话中展示引用的网站源

### 生成物

- 项目生成物列表
- 按工作流、任务、格式、时间筛选
- 预览文本 / Markdown / JSON / SVG / Mermaid 类结果
- 下载生成物
- 发送到邮箱
- 回看来源工作流 / 任务 / 输出节点

## 8.2 第二阶段可做

### 项目知识

- 工作流级知识
- URL 导入
- txt / md 文件导入
- 标签建议
- 引用权重或置顶

### 网站源

- 批量导入 URL
- 站点分类与健康状态
- 站点模板推荐
- crawler 节点一键从网站源预填
- 网站源使用统计

### 生成物

- 收藏 / 置顶
- 站内分享链接
- 生成物二次投递到 webhook / API
- 关联对话上下文再次生成
- 自动归类到项目成果集

## 8.3 当前不做

- 全文向量召回平台
- 网站源自动深度学习规则
- 自动生成复杂爬虫规则引擎
- 生成物版本市场或公开发布平台
- 跨组织复杂协作权限

## 9. 信息架构

## 9.1 推荐产品结构

建议统一放到“项目资产中心”中，而不是拆成三个分散入口。

推荐结构：

- 项目
  - 工作流
  - 资产
    - 知识
    - 网站源
    - 生成物

## 9.2 推荐路由

推荐新增：

- `/projects/:projectId/assets/knowledge`
- `/projects/:projectId/assets/sources`
- `/projects/:projectId/assets/artifacts`

可选折中方案：

- `/projects/:projectId/knowledge`
- `/projects/:projectId/sources`
- `/projects/:projectId/artifacts`

建议优先使用统一 `assets` 路由，便于形成产品心智。

## 9.3 页面入口建议

### 方案 A：项目页二级导航

在项目页增加：

- 工作流
- 资产

进入资产后使用 tab：

- 知识
- 网站源
- 生成物

优点：

- 用户容易理解
- 最贴近项目主线
- 后续易扩展

### 方案 B：工作流编辑器与 Alkaid 面板内的侧入口

在工作流编辑器或 `/assistant` 页面中补充：

- 当前项目知识摘要
- 当前项目网站源摘要
- 最近生成物

此方案适合作为增强入口，而不是主入口。

## 10. 概念模型

## 10.1 项目知识

本质：项目内的规则和经验型文本资产。

适合存放：

- 业务规则
- 输出要求
- 站点抓取经验
- 常见错误与修复建议
- 术语约定

不适合存放：

- 大量网址列表
- 需要强结构化处理的站点信息
- 大批量原始文件

## 10.2 网站源

本质：可执行的数据源资产。

适合存放：

- 网站名称
- 基础 URL
- 示例列表页
- 示例详情页
- 抓取方式建议
- 访问性状态
- 标签与说明

不适合存放：

- 长篇业务规则
- 通用排错经验
- 纯生成结果

## 10.3 生成物

本质：工作流输出结果资产。

适合存放：

- 文档
- 图表
- Mermaid 图
- Markdown 结果
- JSON / 文本导出
- 发送邮件前后需要复用的结果

## 11. 数据结构建议

## 11.1 项目知识

优先复用现有 `alkaid_knowledge`，扩展项目维度。

建议字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | number | 是 | 主键 |
| `user_id` | number | 是 | 所属用户 |
| `project_id` | number | 是 | 所属项目 |
| `workflow_id` | number \| null | 否 | 可选工作流级作用域 |
| `source_type` | string | 是 | `system` / `project` / `workflow` |
| `category` | string | 是 | `best_practice` / `error_repair` / `business_rule` / `scene_template` |
| `target` | string | 否 | 关联对象，如 `crawler` / `ai` / `output` |
| `title` | string | 是 | 标题 |
| `content` | text | 是 | 正文 |
| `tags` | string[] | 否 | 标签 |
| `is_active` | boolean | 是 | 是否启用 |
| `created_at` | datetime | 是 | 创建时间 |
| `updated_at` | datetime | 是 | 更新时间 |

## 11.2 网站源

建议新增独立表，例如：`project_website_sources`

建议字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | number | 是 | 主键 |
| `user_id` | number | 是 | 所属用户 |
| `project_id` | number | 是 | 所属项目 |
| `name` | string | 是 | 网站源名称 |
| `base_url` | string | 是 | 网站基础地址 |
| `entry_url` | string | 否 | 推荐入口页 |
| `list_url_examples` | json/text | 否 | 列表页样例 |
| `detail_url_examples` | json/text | 否 | 详情页样例 |
| `allowed_patterns` | json/text | 否 | 建议抓取的 URL 范围 |
| `blocked_patterns` | json/text | 否 | 不建议抓取的 URL 范围 |
| `crawl_tips` | text | 否 | 抓取提示 |
| `auth_hint` | text | 否 | 登录 / cookie / header 提示 |
| `content_hint` | text | 否 | 正文区域或字段提示 |
| `tags` | string[] | 否 | 标签 |
| `status` | string | 是 | `active` / `disabled` / `invalid` |
| `last_checked_at` | datetime | 否 | 最近校验时间 |
| `last_check_status` | string | 否 | 最近校验结果 |
| `last_check_message` | text | 否 | 校验说明 |
| `created_at` | datetime | 是 | 创建时间 |
| `updated_at` | datetime | 是 | 更新时间 |

说明：

- `crawl_tips` 负责经验说明
- URL 与模式字段负责结构化站点信息
- 网站源不是知识条目的替身，而是单独资产类型

## 11.3 生成物

优先复用现有 `artifacts`。

当前已有关键字段：

- `user_id`
- `workflow_id`
- `task_id`
- `node_id`
- `kind`
- `mime_type`
- `metadata`

MVP 建议：

- 先通过 `workflow -> project` 关系做项目级查询
- 若性能或实现复杂度不理想，再补 `project_id` 冗余字段

建议新增或补充可选字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `project_id` | number | 否 | 冗余项目 ID，便于过滤 |
| `title` | string | 否 | 对外展示标题，默认可等于 `name` |
| `source_session_id` | number | 否 | 可选关联 Alkaid 会话 |
| `is_pinned` | boolean | 否 | 是否置顶 |

## 12. 功能需求

## 12.1 项目知识管理

- 用户可查看项目内全部知识条目
- 用户可按关键字、分类、目标、标签、启停状态筛选
- 用户可创建、编辑、删除、启停知识条目
- 用户可做检索测试，验证哪些知识会被 Alkaid 召回
- Alkaid 回复中应展示命中的知识引用

## 12.2 网站源管理

- 用户可查看项目内全部网站源
- 用户可新增、编辑、删除、启停网站源
- 用户可填写示例 URL、抓取提示、限制说明
- 用户可发起 URL 可访问性校验
- 用户可在结果中看到：
  - 是否可访问
  - 是否重定向
  - 是否疑似登录页、搜索页、异常页
- Alkaid 在生成 crawler 节点时可参考网站源
- Alkaid 回复中应展示命中的网站源引用

## 12.3 生成物管理

- 用户可在项目维度查看所有生成物
- 用户可按工作流、任务、节点、格式、时间筛选
- 用户可预览适合预览的生成物
- 用户可下载生成物
- 用户可通过邮件发送生成物
- 用户可从生成物跳转回来源任务与工作流

## 13. 与 Alkaid 的集成

## 13.1 项目知识注入

在以下场景中自动参与上下文：

- 项目页打开 Alkaid
- 工作流编辑器中打开 Alkaid
- 项目相关对话、诊断、补丁、工作流生成

注入顺序建议：

1. 系统知识
2. 项目知识
3. 工作流级知识

## 13.2 网站源注入

在以下场景中自动参与上下文：

- 用户要求“帮我抓某个网站”
- 用户要求“生成 crawler 工作流”
- 用户提到某个项目内已维护的网站源名称或标签

Alkaid 使用网站源时应优先做：

1. 命中项目网站源
2. 读取结构化站点信息
3. 必要时执行 URL 可访问性检查
4. 再生成 crawler 节点或工作流

## 13.3 引用可见性

用户必须能在回答中感知：

- 本次使用了哪些项目知识
- 本次使用了哪些网站源
- 若生成了工作流，哪些 crawler 节点参考了哪些站点

建议在 Alkaid 回复区展示：

- 引用知识数
- 引用网站源数
- 每条引用的标题 / 名称
- 来源范围

---

## 14. 与工作流的集成

## 14.1 crawler 节点

网站源对 crawler 节点的价值最大。

MVP 集成方式建议：

- Alkaid 生成 crawler 节点前，先检索项目网站源
- 选中网站源后，自动使用其：
  - `base_url`
  - `entry_url`
  - `list_url_examples`
  - `detail_url_examples`
  - `crawl_tips`

第二阶段可做：

- 在 crawler 节点配置面板里直接选择“来源网站源”
- 一键预填 URL 和推荐抓取参数

## 14.2 输出节点

生成物管理直接承接输出节点结果。

要求：

- 输出节点创建的 artifact 自动进入项目生成物列表
- 项目生成物能回溯到：
  - 工作流
  - 任务
  - 输出节点

| `/api/projects/:projectId/sources/:id/check` | POST | 可访问性校验 |
| `/api/projects/:projectId/sources/search` | GET/POST | 给 Alkaid 或页面做筛选搜索 |

## 17. 技术策略建议

## 17.1 项目知识

推荐：

- 复用现有 `alkaid_knowledge`
- 增加 `project_id`、`workflow_id`、`source_type`
- 继续使用 SQL 级过滤和简单召回

不建议本期引入：

- 向量库
- 复杂排序模型

## 17.2 网站源

推荐：

- 独立建表
- 与项目强绑定
- 可访问性检查复用现有 URL 检查能力

原因：

- 网站源是结构化资产，不应与知识文本完全混用
- 后续大概率会扩展为 crawler 配置预填和站点健康度管理

## 17.3 生成物

推荐：

- 复用现有 `artifacts`
- 通过工作流关联到项目
- 前端新增项目级生成物页

若后续项目级查询频繁，再考虑给 `artifacts` 冗余 `project_id`。

## 18. 实施优先级

建议分两阶段推进。

### 第一阶段

- 用户侧项目知识
- 用户侧网站源
- 项目生成物列表页
- Alkaid 引用展示

### 第二阶段

- crawler 节点从网站源一键预填
- 工作流级知识
- 生成物收藏 / 分享 / 二次投递

## 19. 验收标准

## 19.1 项目知识

- 用户能在项目中维护知识条目
- Alkaid 在项目场景中能实际引用这些知识
- 用户能看到知识引用结果

## 19.2 网站源

- 用户能在项目中维护网站源
- 网站源能做可访问性校验
- Alkaid 在 crawler 相关任务中能优先参考网站源

## 19.3 生成物

- 用户能在项目维度看到历史生成物
- 能按来源和格式筛选
- 能预览、下载、邮件发送
- 能回溯到原工作流和任务

---

## 20. 最终建议

从产品命名与实现边界上，建议这样理解：

- “知识库”负责沉淀规则、术语、经验
- “网站源”负责沉淀可执行的数据源
- “生成物”负责沉淀流程结果

不建议把“很多可访问的网址”直接等同于知识库。

更合理的产品表达是：

> 在项目资产中心中，分别管理知识、网站源和生成物，并让 Alkaid 在项目上下文中统一使用这些资产。

这比单独做“用户知识库”更贴近你当前系统，也更容易逐步落地。
