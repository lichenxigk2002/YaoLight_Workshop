# 管理端交互规范

## 1. 目标

本规范用于统一 `admin-frontend` 已实现模块的交互容器选择，减少以下问题：

- 同类操作在不同模块中出现不同交互，造成认知负担
- 新模块缺少判断标准，继续各自演进
- 后续做权限、埋点、移动端适配时缺少统一基线

本规范优先约束：

- 列表页上的查看、创建、编辑、测试、确认类操作
- 复杂模块的页面拆分方式

不适用于当前仍为占位页的模块。

## 2. 容器决策规则

### 2.1 使用 `Modal`

适用于轻操作、短流程、一次性确认：

- 确认删除
- 重置密码
- 测试执行
- 少量字段编辑

要求：

- 字段数量少
- 用户不需要长时间对照列表信息
- 操作完成后通常直接关闭

### 2.2 使用 `Drawer`

适用于依附列表上下文的中重表单或详情查看：

- 列表项详情
- 中等到较重的创建/编辑表单
- 需要保留当前筛选、分页和列表位置的操作

要求：

- 打开后不离开当前列表页
- 适合边看列表边处理单条记录
- 表单字段较多，或需要分区展示

### 2.3 使用独立页面 / 子路由

适用于领域复杂、内容分区明确、用户需要持续停留的场景：

- 多分区配置
- 需要多个二级页签或子路由维护
- 需要稳定 URL 以支持返回、分享、权限控制

要求：

- 不把多个不同领域字段混成一个超大表单
- 详情、能力、计费、日志等可拆为独立子路由

### 2.4 使用页内编辑区域

页内编辑不是默认方案，只允许用于以下情况：

- 当前页面本身就是单一任务页
- 编辑区域不是附着在列表中的局部展开
- 该页没有更合适的抽屉或子路由方案

列表页内的创建/编辑，不再使用“页内展开编辑区”作为默认实现。

## 3. 细则

### 3.1 列表页

- 查看详情优先使用 `Drawer`
- 中重创建/编辑优先使用 `Drawer`
- 测试、确认、短表单优先使用 `Modal`

### 3.2 详情页

- 单一概览页允许在页内切换查看/编辑
- 若详情存在多个领域，必须拆成子路由或页签

### 3.3 一致性要求

- 同一模块内，相同类型操作应使用同一类容器
- 文案应与实际容器一致，不再出现“面板文案 + 抽屉实现”长期混用
- 新模块默认先套用本规范，只有明确理由时才做例外

## 4. 不纳入本次合规范围的占位页

以下模块当前仍为占位页，不纳入本次合规结论：

- `permissions`
- `workflow-templates`
- `node-types`
- `system-configs`
- `operation-logs`

## 6. 后续新增页面默认做法

新增后台页面时，先按以下顺序判断：

1. 这是轻操作还是确认动作？如果是，用 `Modal`
2. 这是列表上下文中的详情或中重表单？如果是，用 `Drawer`
3. 这是复杂领域配置或多分区详情？如果是，用独立页面 / 子路由

如果不满足以上三类，再评估是否允许使用页内编辑区域，并在 PR 或文档中写明原因。
