# 基于 Go 与 React 的低代码智能工作流平台“瑶光工坊”的设计与实现

## 摘要

随着企业数字化转型和业务流程自动化需求的增长，面向数据采集、内容处理和智能分析的应用构建过程对开发效率、流程可视化和系统可扩展性提出了更高要求。低代码技术能够通过图形化建模降低流程搭建门槛，大语言模型为自然语言驱动的流程生成和任务辅助提供了新的实现方式。针对现有工具在可视化编排、网页数据采集、智能生成、执行监控和平台治理等方面协同不足的问题，本文设计并实现了低代码智能工作流平台“瑶光工坊”。

系统采用前后端分离和模块化设计，围绕“可视化建模、任务执行、智能生成、结果沉淀与开放复用”构建整体功能体系。平台将网页数据采集、结构化处理、大模型调用、流程控制和结果导出等能力抽象为可组合的工作流节点，并通过统一的图结构存储、变量上下文、节点执行记录和任务日志机制支撑流程运行。围绕自然语言生成工作流的需求，本文设计了“瑶光星（Alkaid）”智能助手，通过能力说明、知识检索、工具调用、试跑校验、补丁修复、报告生成和人工确认等环节，形成从用户需求到可执行工作流的生成闭环。

系统实现过程中重点完成了五方面工作：构建基于 DAG 依赖解析的并发工作流执行引擎，并加入任务快照与失败节点续跑机制；设计基于源码配置抽取的能力说明服务，用于减少节点能力描述与实际实现之间的不一致；实现待确认工作流、待确认补丁和任务模式报告机制，支持人机协同式工作流生成；提供代码节点与 AI 代码修复能力，增强复杂数据转换场景下的表达能力；集成项目资产、开放接口、权限控制、通知和 AI 工具接入等支撑能力，形成较完整的低代码工作流系统。测试结果表明，系统能够完成典型的数据采集、AI 分析、结果导出和外部调用流程，具备一定的可扩展性和工程应用价值。

**关键词：** 低代码；工作流引擎；大语言模型；智能体；AI 辅助生成

## Abstract

With the development of digital transformation and business process automation, applications for data acquisition, content processing, and intelligent analysis require higher development efficiency, better process visualization, and stronger system extensibility. Low-code technology lowers the barrier to process construction through visual modeling, and large language models provide new possibilities for natural-language-driven workflow generation and task assistance. To address the insufficient integration of visual orchestration, web data acquisition, intelligent generation, execution monitoring, and platform governance in existing tools, this paper designs and implements a low-code intelligent workflow platform named YaoLight Workshop.

The system adopts a front-end/back-end separated and modular architecture, and its functional design is organized around visual modeling, task execution, intelligent generation, result persistence, and open reuse. Capabilities such as web data acquisition, structured processing, large-model invocation, flow control, and artifact export are abstracted as composable workflow nodes. A unified graph model, variable context, node execution records, and task logs are used to support workflow execution. For natural-language workflow generation, an intelligent assistant named Alkaid is designed. It combines capability descriptions, knowledge retrieval, tool invocation, trial execution, patch repair, report generation, and human confirmation to form a closed loop from user requirements to executable workflows.

The implementation focuses on five aspects. First, a DAG-based concurrent workflow execution engine is built, with task snapshots and failed-node resume support. Second, a source-code-driven capability description service is designed to reduce inconsistency between node descriptions and actual implementations. Third, pending workflows, pending patches, and task-mode reports are implemented to support human-in-the-loop workflow generation. Fourth, a code node and an AI-assisted code repair mechanism are provided to enhance data transformation capability in complex scenarios. Fifth, project assets, open interfaces, permission control, notifications, and AI tool access are integrated as platform support capabilities. The test results show that the system can support typical processes such as web data acquisition, AI analysis, artifact export, and external invocation, and has practical extensibility and engineering value.

**Key Words:** low-code; workflow engine; large language model; agent; AI-assisted generation

## 前言

随着数字经济和人工智能技术的发展，信息采集、内容处理、数据分析和流程自动化需求不断增加。传统软件开发方式虽然灵活，但在需求变化频繁、流程需要快速调整和复用的场景中，存在开发周期长、维护成本高、非技术用户参与困难等问题。低代码技术能够通过可视化建模降低系统构建门槛，大语言模型又为自然语言生成流程、辅助配置和智能修复提供了新的可能。因此，研究低代码平台与人工智能能力的结合，对于提升自动化流程构建效率和拓展智能工作流应用具有一定意义。

本课题旨在设计并实现一个面向数据采集、内容处理与智能分析场景的低代码智能工作流平台“瑶光工坊”。研究范围包括可视化工作流建模、节点数据流转、任务执行调度、网页信息采集、大模型调用、AI 辅助生成、结果导出和开放调用等内容。系统需要达到的主要技术要求是：前端能够完成节点拖拽、连线、配置和状态展示；后端能够完成工作流存储、任务调度、日志记录和节点执行管理；平台支持多类型节点组合、变量上下文传递、并发执行、失败节点续跑和人工确认式 AI 生成，具备一定的扩展性、安全性和可维护性。

从国内外发展情况看，低代码平台、流程自动化工具和大模型应用构建平台已较为活跃，但仍存在能力边界分散的问题。传统低代码平台多侧重表单、审批和企业轻量应用，对网页采集、动态内容处理和 AI 分析支持有限；部分 AI 应用平台更关注对话、知识库和智能体编排，对通用工作流执行、任务监控、失败恢复和平台治理支持不足；自然语言生成工作流的方案也容易停留在一次性生成层面，缺少校验、修复和人工确认机制。

本课题以实际流程自动化需求为出发点，以工程可用性和可扩展性为指导思想，重点解决以下问题：如何将业务流程抽象为节点和边组成的图结构；如何通过变量上下文实现节点间数据传递；如何构建支持依赖调度、条件分支、并发执行和失败续跑的执行引擎；如何使 AI 助手根据平台能力生成或修正工作流，并避免直接覆盖用户结果。本文采用文献与产品调研、需求分析、系统建模、模块化设计、工程实现和测试验证相结合的方法，完成系统设计、核心功能实现和典型流程验证。

## 第1章 绪论

### 1.1 研究背景

在数字经济背景下，企业软件系统逐步从信息录入与查询工具发展为面向业务流程协同、数据采集处理和智能决策支持的综合平台。传统软件开发通常需要前端、后端、数据库和运维人员协同完成，开发门槛较高，迭代周期较长。在需求变化频繁或任务流程较明确的场景中，用户往往希望快速搭建“采集数据—清洗处理—模型分析—导出结果”的自动化流程，纯代码开发模式难以满足快速验证和持续调整的需求。

低代码技术为这一问题提供了有效思路。通过节点拖拽、可视化连线和配置式建模，复杂流程可以被抽象为图结构，并在统一引擎中执行。与此同时，大语言模型在自然语言理解、代码生成、工具调用和任务规划等方面表现出越来越强的能力，使“用户用一句话描述需求，系统自动生成工作流”的交互方式成为可能。尤其在数据采集与 AI 内容处理场景中，用户往往并不关心代码细节，而更关心任务是否能够稳定执行、结果是否可导出、系统是否便于后续修改。

现有低代码平台和 AI 应用构建平台在能力覆盖上各有侧重。表单与审批类平台主要面向企业轻量应用，复杂网页抓取、动态渲染和多节点数据处理能力相对有限；大模型应用构建平台主要面向智能问答、知识库和智能体编排，对通用工作流执行、任务调度和平台治理的支持仍有进一步扩展空间。基于此，本文面向数据采集与智能分析场景，设计融合可视化工作流、并发执行引擎、多模型接入、网页爬虫、AI 自动生成、开放 API 与平台治理能力的一体化系统。

### 1.2 国内外研究现状

低代码与工作流技术的发展已较为成熟。国内外大量平台通过图形化建模提升了开发效率，但多数系统在能力边界上有所侧重。传统低代码平台主要适用于表单、审批和数据录入场景，自动化平台更强调第三方服务集成和任务触发，大模型应用平台则重点关注 Prompt、知识库和智能体编排。综合来看，将低代码工作流、通用爬虫、多模型调用和平台治理进行系统化融合的工程实践仍有研究空间。

在 AI 辅助工作流生成方向，已有研究开始尝试利用大语言模型生成结构化流程定义，并通过提示约束、检索增强和格式校验提高生成质量。但许多方案仍停留在一次性输出层面，对生成后的逻辑校验、试运行验证、失败修复以及人机协同确认的研究不足。对于实际执行的工作流系统而言，仅靠单次 JSON 生成并不足以保证可用性。

在系统架构层面，前后端分离与模块化服务组织已成为主流实践。前端负责交互界面和可视化建模，后端负责服务编排、数据存储和执行控制，有助于兼顾开发效率和运行性能。结合关系型数据库对结构化与半结构化数据的支持，以及缓存系统在临时状态和高频访问场景中的辅助能力，可以为低代码工作流平台提供较稳定的实现基础。

### 1.3 研究目的与意义

本文的研究目标是设计并实现一个面向数据采集、内容处理与智能分析场景的低代码智能工作流平台“瑶光工坊”。系统支持用户通过可视化方式搭建工作流，也支持通过自然语言由 AI 助手生成工作流，并对生成结果进行校验、试跑和人工确认，从而降低用户使用复杂自动化能力的门槛。

本课题的理论意义在于：探索低代码工作流平台与大语言模型深度融合的实现路径，验证“自然语言到工作流”的工程闭环是否可行，并为 AI 辅助软件工程和智能流程编排提供实证案例。本课题的实践意义在于：将多模型调用、网页爬虫、数据清洗、代码执行、任务调度、失败续跑、结果导出、开放接口和 AI 工具接入等能力整合到统一平台中，形成一个具备真实业务承载能力的系统原型，可服务于舆情监测、竞品分析、信息采集和内容自动化生成等场景。

### 1.4 本文主要工作与创新点

本文围绕系统需求分析、总体架构设计、数据库设计、工作流引擎实现、AI 助手设计与平台支撑能力构建等方面开展研究，完成了一个可运行的全栈系统。系统由用户端、管理后台、后端服务和数据存储组成，重点覆盖工作流编辑、工作流执行、AI 辅助生成、任务监控、结果导出和开放调用等能力。

本文的主要创新点体现在以下几个方面：

1. 提出并实现了面向低代码工作流平台的 Agentic 生成闭环。系统将能力说明、知识检索、工具调用、试跑校验、失败修复和人工确认整合为一个可解释、可追踪的生成流程。
2. 设计了基于源码配置抽取的能力说明机制。系统通过配置抽取器从节点执行源码中提取配置字段、默认值和变量引用特征，用于动态更新 Alkaid 的能力说明，减少文档与代码不一致导致的生成错误。
3. 实现了支持并发执行的工作流引擎。系统以图结构描述流程，结合依赖判断、节点状态管理、节点执行记录和任务日志记录，实现了从单节点执行到整图并发调度的统一控制。
4. 构建了待确认工作流与待确认补丁机制。AI 生成结果先进入待确认区，用户可选择整图应用或补丁应用，增强了系统安全性与可控性。
5. 设计了任务快照与失败节点续跑机制。系统在执行时保存工作流节点、连线、运行输入和运行上下文，重试时复用已完成节点的输出，仅重新调度失败节点及其下游节点，降低长流程失败后的重复成本。
6. 构建了项目资产与开放服务能力。系统支持项目知识、网站来源、工件沉淀、Workflow API 发布、API Key 管理和调用记录查询，使工作流结果既能在平台内查看，也能作为外部系统服务被复用。代码节点、MCP 接入、通知、账务和 RBAC 等功能作为平台支撑能力，为系统扩展和实际运行提供辅助保障。

## 第2章 相关技术与理论基础

### 2.1 React 与可视化工作流编辑技术

本系统前端采用 React 19 与 TypeScript 进行开发。React 具有组件化、状态驱动和生态成熟等特点，适合构建交互复杂、状态较多的单页应用。结合 React Router 可实现多页面前端路由组织，结合 Zustand 可进行局部状态与共享状态管理。

工作流编辑器部分采用 React Flow 作为核心可视化编排库。React Flow 支持节点拖拽、边连接、缩放平移、自定义节点渲染和句柄控制，适合表达工作流这种图结构数据。系统在此基础上进一步封装了 12 类节点组件、对应的配置面板和节点测试能力，实现了从图形交互到业务配置的统一界面。

### 2.2 Go、Gin 与 GORM 技术基础

后端采用 Go 语言实现。Go 天然支持高并发编程，语法简洁，部署方便，适合构建高吞吐、低延迟的服务系统。Gin 是 Go 生态中常用的轻量级 Web 框架，具有中间件机制清晰、路由性能良好等特点，适合承载认证、工作流接口、开放 API 和管理接口等多种 HTTP 服务。

数据访问层使用 GORM 完成对象关系映射。GORM 通过模型定义、关联查询和自动迁移降低了数据库操作复杂度，并支持 JSONB 等类型扩展，能够适配工作流节点配置、AI 参数和通知元数据等结构化与半结构化并存的数据形态。

### 2.3 PostgreSQL、Redis 与平台数据管理

PostgreSQL 作为系统主数据库，承担用户、项目、工作流、任务、AI 模型、知识库、通知、订单与权限等核心数据的持久化。相比传统只存储关系型字段的数据库设计，本系统大量使用 JSONB 存储节点配置、模型参数、工件元数据、运行上下文等动态结构，既保持了表结构稳定性，又保留了较高的扩展性。

Redis 主要用于缓存与临时状态支持，例如验证码、OAuth 绑定过程中的临时状态等。对于需要高频读取但不要求长期落盘的场景，Redis 可降低数据库访问压力，提升系统响应速度。

### 2.4 工作流引擎与 DAG 执行思想

工作流本质上可以看作由节点和有向边构成的图结构。节点表示处理步骤，边表示数据依赖或控制依赖。对于无循环主链流程，可以视作 DAG（有向无环图）进行依赖调度；对于包含条件和循环的场景，则需要在运行时结合分支状态和输入数据进行动态控制。

本系统的工作流引擎采用“节点配置 + 边关系 + 变量上下文”的设计方式。执行时，系统先构建节点与边关系，再根据上游节点执行状态判断下游节点是否就绪；对于 AI 节点可启用流式输出，对于条件节点则通过分支句柄决定执行路径。为提高吞吐量，系统还设计了并发执行流程，对无依赖冲突的节点进行并行调度。对于长链路任务，系统进一步引入任务快照与续跑状态，用于在失败后复用已完成节点的输出，提升复杂流程的可恢复性。

### 2.5 大语言模型、RAG 与 Agentic Workflow

大语言模型为低代码平台提供了新的交互方式。用户可以通过自然语言描述目标任务，由系统生成流程框架与节点参数。由于工作流需要满足节点类型、连线关系、变量引用和执行约束等要求，直接生成工作流 JSON 容易出现字段缺失、结构错误和场景不匹配等问题。

为此，系统引入 Agentic Workflow 思路，将 AI 助手设计为具备工具调用能力的工作流规划组件。在该模式下，模型先读取平台能力说明，再结合知识库检索、节点规格查询、URL 可访问性检查、工作流试跑等工具逐步收集上下文，最后输出待确认工作流或补丁。系统还通过知识检索与规则注入对提示词进行增强，这一过程可视为面向平台规则的轻量 RAG。

### 2.6 ChromeDP 动态网页爬虫技术

网络数据采集是本系统的重要使用场景之一。静态页面可通过 HTTP 请求与解析器获取，但大量现代网站依赖 JavaScript 动态渲染，普通请求方式难以获得完整内容。为此，系统采用 ChromeDP 实现无头浏览器抓取，从而支持动态页面加载、页面等待、HTML 获取和相关扩展能力。

为了提高爬虫节点的可用性，系统还引入了 URL 可访问性检查、超时设置、重试控制、请求头与 Cookie 配置等机制，并通过后台爬虫规则管理实现抓取经验的沉淀与复用。

### 2.7 SSE、WebSocket 与实时反馈技术

工作流执行与 AI 会话具有明显的实时性需求。用户需要在执行过程中查看节点状态变化、日志和中间结果。为满足该需求，系统在工作流执行与 Alkaid Agentic 会话中采用 SSE 进行流式推送，在站内通知模块中采用 WebSocket 推送消息，从而形成面向不同场景的实时反馈机制。

### 2.8 MCP 与 AI 工具接入技术

模型上下文协议（Model Context Protocol, MCP）为 AI 工具访问外部系统提供了统一的工具描述与调用方式。MCP 可使 Codex、Cursor、Claude Desktop 等 AI 客户端以结构化工具的形式读取业务对象、诊断问题和触发受控操作。本系统将 MCP 定位为 AI 工具接入层，通过独立 Token、权限范围、调用日志和管理员策略控制，使外部 AI 工具能够在授权范围内访问项目、工作流、任务、工件和知识库等对象。

## 第3章 系统分析与总体设计

### 3.1 系统角色分析

从业务角度看，系统主要包含四类角色。第一类是普通用户，负责创建项目、维护工作流、执行任务、调用 AI 助手和查看导出结果；第二类是管理员，负责模板、节点类型、爬虫规则、AI 模型、账务和通知等平台级资源治理；第三类是外部系统调用方，其通过已发布的 Workflow API 调用指定工作流并获取执行结果或工件；第四类是外部 AI 工具调用方，其通过 MCP Token 访问用户授权范围内的项目、工作流、任务日志和工件信息，辅助用户进行诊断、分析和受控执行。

### 3.2 功能需求分析

系统的核心功能需求可以概括为以下几个方面。

首先是工作流建模需求。用户需要通过拖拽节点和连接边快速构建自动化流程，并在图形界面中完成节点参数配置、变量引用和流程调整。系统应支持至少开始、爬虫、数据清洗、AI、代码、条件、转换、循环、合并、延迟、输出和结束等节点类型。

其次是工作流执行与监控需求。系统不仅要能够执行工作流，还要记录任务运行状态、节点执行结果、错误信息和任务日志，并支持在前端实时展示执行进度。对于包含多个爬虫、AI 或导出节点的长流程，系统还应支持失败节点续跑，避免单个节点失败导致整条链路必须从头执行。

再次是 AI 辅助生成需求。用户希望通过自然语言直接表达目标，由 Alkaid 自动生成流程，并在生成过程中理解节点能力、结合知识库检索结果进行规划，在必要时通过试跑和修复机制提高生成成功率。

此外，系统还需要覆盖项目资产管理、多模型接入、开放 API、MCP 工具接入、站内通知、支付与计费、后台管理和权限控制等平台级支撑需求。这些能力服务于工作流运行、结果复用和系统管理，不作为本文的主要研究对象展开。

### 3.3 非功能需求分析

非功能需求主要体现在以下几个方面：

- **可扩展性**：节点类型、AI 提供商、输出格式和后台管理能力应支持持续扩展。
- **可维护性**：系统需采用明确的模块边界，降低多功能平台后期演进成本。
- **可用性**：AI 生成结果不能直接覆盖用户画布，必须保留人工确认能力。
- **可观测性**：需要具备任务日志、节点执行记录、通知和操作日志等追踪能力。
- **性能与并发性**：执行引擎应支持并发调度与长任务运行。
- **可恢复性**：长流程失败后应尽量复用历史执行结果，并支持失败节点及其下游节点续跑。
- **安全性**：接口需具备 JWT、API Key、MCP Token、RBAC 与 Hook 风控等多层控制，系统预设 AI 节点执行前还需校验用户 Token 余额，避免无额度情况下继续产生模型调用成本。

### 3.4 系统总体架构设计

系统总体采用前后台分离架构，并进一步拆分出独立的管理后台前端。整体可分为四层。

第一层是用户交互层，包括普通用户前台和管理后台。普通用户前台负责项目、工作流、AI 助手、任务结果和个人中心等功能；管理后台负责平台级资源和治理能力。

第二层是接口服务层，由 Gin 提供统一 REST API，同时在部分场景下扩展 SSE 和 WebSocket。该层承接登录认证、工作流操作、任务执行、开放调用、通知推送和后台管理等请求。

第三层是业务服务层，由多个模块组成，包括用户、项目、工作流、任务、AI、Alkaid、Artifact、开放 API、权限、通知、账务和 MCP 等。工作流、任务与 Alkaid 是核心业务模块，其余模块为平台运行提供支撑。

第四层是数据与基础设施层，包括 PostgreSQL、Redis、本地或对象存储型文件系统、外部 AI Provider 接口和外部网站资源。工作流执行结果和导出文件统一沉淀为 Artifact，以便复用。

## 第4章 系统详细设计与实现

### 4.1 用户认证与权限控制设计

用户模块提供注册、登录、邮箱验证码验证、OAuth 登录、密码重置、头像管理和个人资料维护等能力。用户实体除用户名、邮箱、密码等基础字段外，还维护 Token 余额、邀请关系、OAuth 绑定状态和偏好设置等信息。系统同时通过邀请码与邀请记录支持邀请裂变场景。

权限治理部分采用 RBAC 模式实现。系统通过 `roles`、`permissions`、`role_permissions` 和 `user_roles` 四张表实现管理员角色与资源权限控制。管理后台各接口通过权限中间件进行校验，不同资源采用 `resource:action` 风格的细粒度权限编码，实现用户管理、模型管理、任务查看、账务操作和通知发送等能力的差异化控制。

### 4.2 工作流可视化建模设计

工作流建模部分以前端可视化画布为核心。用户在编辑器中拖拽节点、配置参数并建立边连接，前端将图结构以节点数组和边数组形式保存到后端。后端在保存时会将每个节点转化为 `workflow_nodes` 表中的持久化记录，并根据边关系构建连接信息。同时，系统还支持注释卡片，用于在画布中记录说明、备注和设计思路，从而提升复杂流程的可维护性。

在节点设计上，系统支持 12 类节点，覆盖从输入、采集、清洗、AI 处理、脚本处理、分支控制到输出结束的完整链路。开始节点用于定义初始输入，爬虫节点负责采集网页内容，数据清洗节点用于清理和标准化文本，AI 节点负责大模型处理，代码节点允许用户通过受限 JavaScript 脚本完成灵活的数据处理，条件节点决定分支，转换节点进行映射或过滤，循环节点处理数组输入，合并节点汇聚多路数据，延迟节点控制时间，输出节点负责结果导出，结束节点则标记流程终止。

### 4.3 变量上下文与数据流设计

为了支持节点之间的数据传递，系统设计了变量上下文机制。每个节点执行结束后，会将自身输出写入变量上下文，并按 `nodeId.variableName` 形式建立索引。下游节点可通过 `{{nodeId.variableName}}` 或更深层路径形式引用上游结果。对于对象类型数据，系统可进一步解析字段路径，实现例如 `{{start-1.data.url}}` 这样的嵌套访问。

这一设计减少了工作流节点对硬编码输入的依赖，使节点可以围绕统一数据流进行动态拼接，从而提高了可组合性和复用性。与此同时，变量上下文还为 AI 节点、条件节点和转换节点的配置模板解析提供了基础支撑。

### 4.4 工作流执行引擎设计

工作流执行引擎是系统后端的核心部分。执行时，系统首先根据节点和边构建执行请求，然后识别开始节点，初始化数据流与变量上下文，再按节点依赖关系调度下游节点。执行器在依赖调度基础上引入并发执行逻辑，对于依赖已满足且互不冲突的节点，可同时进入执行状态，从而提高整体执行效率。

引擎对任务级和节点级状态分别进行记录。任务层通过 `tasks` 表记录整体运行状态、输入、输出、错误信息和耗时；节点层通过 `task_node_executions` 表记录每个节点的输入、输出、状态、错误和执行时长；日志层通过 `task_logs` 表记录调试、信息、警告和错误日志。这样既支持前端实时展示，也为管理员排查问题提供了数据基础。

### 4.5 任务快照与失败续跑机制设计

为提高长流程的可靠性，执行引擎设计了任务快照与失败节点续跑机制。系统在任务创建时将工作流节点、边、运行输入和运行元数据保存到执行上下文中。用户对失败任务发起续跑时，后端首先从快照中恢复原始执行请求，再分析历史节点执行记录，将失败、超时或已开始但被取消的节点作为续跑起点，并把这些节点的下游节点加入重新调度集合。对于已经完成且不在重新调度集合中的节点，系统复用其输出数据作为上下文，从而避免重复执行已经成功的爬虫、AI 或导出步骤。

### 4.6 瑶光星智能助手设计与实现

Alkaid 是系统中负责智能生成与辅助诊断的核心模块。系统将其设计为面向工作流生成的 Agentic 助手。会话层通过 `alkaid_sessions` 和 `alkaid_messages` 持久化用户会话、消息内容和中间状态；知识层通过 `alkaid_knowledge` 和 `alkaid_node_specs` 管理通用知识、项目知识、工作流级知识和节点规格约束。

在执行链路上，Alkaid 会先读取能力说明，再结合知识检索、当前工作流上下文、节点规格查询、URL 可访问性检查等工具逐步规划，随后生成待确认工作流或待确认补丁。系统通过 SSE 向前端持续推送阶段变更、计划步骤、工具步骤、生成内容以及待确认结果，实现“过程可见”的智能交互体验。

为减少 AI 生成错误，系统引入了多重保护机制。首先，`CapabilitiesService` 提供结构化节点能力说明；其次，`config_extractor` 可从节点执行源码中自动抽取配置字段和默认值；再次，Alkaid 在生成后还可以触发试跑与错误反馈，并在需要时调用补丁机制对现有工作流进行增量修改。最后，在写回画布前，系统还支持 `BeforeApplyWorkflow` 等 Hook 进行风控和人工确认。

随着功能演进，Alkaid 已扩展出分析、解释、修复、试跑调试和报告生成等任务模式。前端通过任务模式徽标、进度卡片、报告卡片和待确认区展示 Agent 当前阶段；后端通过会话运行管理器避免同一会话并发执行多个长任务，并支持中断当前任务。该设计增强了 AI 助手在复杂操作中的可解释性和可控性。

### 4.8 AI 模型适配与代码节点设计

系统在 AI 能力接入上采用 Provider 抽象。前端 AI 节点支持通过注册表动态加载不同提供商配置组件，后端则通过提供商工厂与统一接口封装各类模型调用差异。系统将用户自定义模型配置和平台管理模型主数据进行区分，前者面向用户侧模型调用，后者用于统一维护模型能力、价格规则和运营治理配置。围绕模型调用成本，系统进一步设计了 Stardust 计费体系，使系统预设模型的调用能够被统计、审计和管控。

代码节点用于弥补纯配置节点在复杂数据转换上的表达不足。用户可在节点配置面板中选择语言、输入模式、超时时间和控制台日志开关，并编写脚本处理上游节点输入。系统现阶段优先支持 JavaScript 运行时，后端通过独立 `node -e` 子进程执行脚本，并将 `input`、`vars`、`node` 和受控 `console` 注入运行上下文。为降低风险，运行时设置了超时时间、最大日志行数、单行日志长度和结果体大小限制，避免脚本长时间阻塞或输出过大数据。

代码节点的输出统一包含 `result`、`stdout`、`stderr`、`metrics` 和 `metadata` 字段，其中 `result` 作为下游节点主要输入，`stdout` 与 `stderr` 用于前端预览和问题排查。由于用户编写脚本时可能出现语法错误、字段引用错误或返回结构不符合预期，系统还提供 AI 代码修复能力。前端展示修复结果后由用户确认应用，避免 AI 自动覆盖原代码。

### 4.9 平台支撑能力设计

除核心工作流和瑶光星能力外，系统还实现了若干平台支撑模块。任务调度模块支持 Cron 定时触发和 Webhook 外部触发，并通过调度运行记录保存每次触发的状态、输入、错误信息和关联任务。爬虫与数据处理能力既体现在工作流节点中，也体现在后台爬虫规则管理中，系统可通过 URL 可访问性检查、ChromeDP 动态抓取、数据清洗和转换节点支撑网页数据采集场景。

项目资产模块用于沉淀工作流执行过程中产生和复用的数据，包括项目知识、网站来源和输出工件等。输出节点通过导出工厂生成 Artifact，并支持 JSON、Markdown、Text、PDF、DOCX、Mermaid、Timeline、Sankey、Network 以及 Chart(SVG) 等多种格式。开放 API 模块允许用户将工作流发布为可调用服务，并通过 API Key、调用记录、状态查询和工件下载实现外部系统复用。

MCP 模块面向 Codex、Cursor、Claude Desktop 等外部 AI 工具提供结构化访问能力。系统为 MCP 单独设计 Token、权限范围和调用日志，使外部 AI 工具能够在授权范围内读取项目、工作流、任务日志、节点执行记录和工件信息，并在受控条件下触发执行类操作。通知、互动、账务、应用日志和操作日志等模块则为系统运营、用户协作、模型成本管控和审计追踪提供辅助支撑。

### 5.3 典型流程测试方案

本文建议选取以下典型业务流程作为实验案例：

1. **网页信息采集与总结流程**：开始节点输入目标网址，爬虫节点抓取正文，数据清洗节点去除噪声，AI 节点完成总结，输出节点导出 Markdown 或 PDF。
2. **批量列表处理流程**：开始节点输入数组数据，循环节点遍历，AI 节点逐项分析，合并节点整合结果，输出节点导出 JSON。
3. **AI 自动生成流程**：用户通过自然语言描述目标任务，Alkaid 自动生成工作流，进行试跑和修复后，用户确认写回画布。
4. **开放 API 调用流程**：已发布的工作流通过 API Key 被外部系统调用，系统返回结果或提供工件下载地址。
5. **代码节点处理流程**：开始节点输入结构化 JSON，代码节点进行字段筛选、统计或重组，输出节点导出 JSON，验证脚本执行、日志采集和结果限制。
6. **失败节点续跑流程**：构造包含爬虫、AI、代码和输出节点的长链工作流，使其中一个中后段节点失败，确认续跑时复用上游成功节点输出，仅重新执行失败节点及其下游节点。
7. **AI 工具接入验证流程**：通过本地 MCP Server 查询工作流、任务详情、任务日志和节点执行记录，验证外部 AI 工具能否在授权范围内完成诊断和受控操作。

### 5.6 系统不足分析

系统已覆盖主要平台能力，但仍存在以下不足：

1. 部分平台治理能力仍需继续完善，例如系统配置页和更细粒度的全局策略管理。
2. AI 生成链路已具备多轮规划、报告和补丁机制，但在复杂长链工作流场景下，生成质量仍依赖模型能力与知识覆盖度。
3. 代码节点目前主要支持 JavaScript，Python 运行时仍处于预留状态；后续若支持更多语言，需要进一步加强沙箱隔离和资源限制。
4. 输出与图表能力已具备基础实现，但在排版美观性、模板多样性和复杂图表适配方面仍有提升空间。
5. 测试数据和性能指标需要进一步标准化采集，以便形成更完整的定量评估。

## 第6章 结论与展望

### 6.1 结论

本文围绕低代码工作流、AI 辅助生成、网页数据采集与平台工程治理等需求，设计并实现了一个基于 Go 与 React 的低代码智能工作流平台“瑶光工坊”。系统采用前后端分离和模块化架构，以可视化工作流编辑器为用户操作入口，以后端任务执行引擎为流程运行核心，将网页爬虫、数据清洗、AI 分析、代码处理、条件分支、循环控制、结果导出和开放调用等能力组织为可组合的节点体系，完成了从流程建模、任务执行、状态追踪到结果沉淀的完整链路。

通过本课题的设计与实现，可以得到以下结论。

第一，低代码工作流平台能够有效降低数据采集与智能分析类任务的构建成本。系统通过 React Flow 实现节点拖拽、连线和配置，通过 Go 后端完成节点持久化、边关系解析、变量上下文构建和任务调度，使用户能够以图形化方式搭建“采集数据—处理数据—模型分析—导出结果”的自动化流程。与传统纯代码开发方式相比，该模式更适合流程结构明确、需要频繁调整和复用的业务场景。

第二，基于 DAG 思想的执行引擎能够支撑较复杂的工作流运行。系统在执行过程中根据节点依赖关系判断就绪状态，对无依赖冲突的节点进行并发调度，并结合条件节点、循环节点、合并节点和延迟节点支持不同类型的控制流。同时，任务表、节点执行记录和任务日志共同构成了可观测的数据基础，使前端能够实时展示任务进度，也便于后续定位错误和分析执行结果。

第三，任务快照与失败节点续跑机制提升了长流程任务的可恢复性。系统在任务创建时保存工作流节点、边、运行输入和上下文快照，在续跑时识别失败节点及其下游节点，并复用已完成节点的输出结果。该机制能够减少长流程失败后的重复执行成本，尤其适用于包含网页爬虫、大模型调用和文件导出等耗时步骤的场景。

第四，大语言模型可以与低代码平台形成较完整的智能生成闭环。本文设计的 Alkaid 智能助手并未停留在一次性生成工作流 JSON 的层面，而是结合能力说明、知识检索、节点规格查询、工具调用、试跑校验、补丁修复、报告生成和人工确认等环节，降低了 AI 生成结果不可控的问题。待确认工作流与待确认补丁机制也保证了用户在最终写回画布前拥有审核和控制权。

第五，低代码智能工作流平台需要配套的平台支撑能力才能具备工程应用价值。本文实现的项目资产、Artifact 工件、Workflow API、MCP 工具接入、AI 模型适配、权限控制、通知、账务和后台管理等模块，使工作流结果不仅能够在平台内部查看，也能够被外部系统和外部 AI 工具复用。这说明低代码平台的核心竞争力不仅在于编辑器本身，也在于执行、治理、开放和复用能力的综合设计。

总体来看，本文完成了“瑶光工坊”低代码智能工作流平台的主要功能设计、核心模块实现和测试验证。系统能够支持典型的网页采集、AI 分析、结构化处理、结果导出和外部调用流程，验证了低代码工作流与大语言模型、Agentic Workflow、开放 API 和 MCP 工具接入相结合的可行性。该系统为面向数据采集与智能分析场景的低代码平台设计提供了一种可参考的工程实现方案。

### 6.2 展望

受开发周期、测试数据和应用场景范围限制，系统仍存在进一步完善空间。后续工作可以从以下几个方面继续展开。

第一，继续提升 Alkaid 在复杂流程场景下的规划与修复能力。后续可引入更细粒度的自动评估机制，对生成工作流的节点完整性、变量引用正确性、边关系合理性和执行结果稳定性进行更系统的检查，从而提高自然语言生成工作流的成功率。

第二，完善平台治理和系统配置能力。当前系统已经具备权限控制、通知、账务、日志和后台管理等基础能力，后续可进一步补充统一配置中心、对象存储后端、多租户隔离、全局策略管理和更细粒度的审计能力，使平台更适合长期运行和团队协作。

第三，增强代码节点运行时安全性与表达能力。现阶段代码节点主要支持 JavaScript 运行时，后续可逐步扩展 Python 等语言支持，同时引入更严格的沙箱隔离、资源限制、依赖管理和安全审计机制，避免灵活性提升带来的运行风险。

第四，优化输出工件与可视化展示能力。系统已支持 JSON、Markdown、PDF、DOCX、Mermaid、Chart 等多种导出形式，后续可继续完善模板市场、图表样式、报告排版和多格式转换能力，使工作流执行结果更适合正式交付和业务汇报。

第五，补充更系统的性能测试与用户可用性研究。后续可围绕并发执行效率、失败续跑收益、AI 生成可用率、Workflow API 响应时间和 MCP 诊断效率等指标进行量化实验，并结合真实用户操作反馈优化交互流程与系统稳定性。

综上所述，低代码平台与大语言模型的结合具有较强的应用潜力。随着模型能力、工具调用协议和平台工程能力的进一步成熟，低代码智能工作流系统有望在信息采集、内容生产、运营分析、知识管理和企业自动化等场景中发挥更大作用。
