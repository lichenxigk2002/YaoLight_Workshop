# 基于 Go 与 React 的低代码智能工作流平台“瑶光工坊”的设计与实现

## 摘要

随着企业数字化转型和业务自动化需求的持续增长，传统以人工编码为主的软件开发与数据处理方式逐渐暴露出开发周期长、维护成本高、业务响应慢等问题。低代码平台通过可视化建模降低了应用构建门槛，而大语言模型的发展又进一步推动了以自然语言驱动系统构建的可能性。针对现有平台在“可视化编排、AI 自动生成、复杂网页数据采集、私有化部署与平台治理”方面集成不足的问题，本文设计并实现了一个基于 Go 与 React 的低代码智能工作流平台“瑶光工坊”。

本系统采用前后台分离架构，前端基于 React 19、TypeScript、React Flow 与 Ant Design 实现可视化工作流编辑器及用户交互界面，后端基于 Go、Gin、GORM、PostgreSQL 与 Redis 构建工作流执行与平台服务能力。系统围绕工作流建模、执行、调度和智能生成四条主线展开，提供了开始、爬虫、数据清洗、AI 处理、条件分支、数据转换、循环、合并、延迟、输出和结束等 11 类节点，支持工作流保存、执行、流式反馈、任务日志记录、工件导出与开放 API 发布。在智能生成方面，本文设计了“瑶光星（Alkaid）”AI 助手，引入 Agentic Workflow 思路，通过能力说明、知识检索、工具调用、试跑校验、补丁修复和人工确认等机制，实现从自然语言需求到结构化工作流的自动生成与安全写回。

与传统低代码平台相比，本系统具有以下特点：一是构建了支持 DAG 依赖解析与节点级并发调度的工作流执行引擎；二是实现了基于源码配置抽取的能力说明服务，降低了 AI 生成阶段的知识漂移风险；三是引入待确认工作流与待确认补丁机制，增强了人机协同与系统可控性；四是将开放 API、工件导出、通知、计费和 RBAC 权限治理等平台能力纳入统一架构，提升了系统的可扩展性与工程完整性。本文最后从功能正确性、典型流程执行和平台可扩展性等角度对系统进行分析，并总结系统当前不足与后续优化方向。

**关键词：** 低代码；工作流引擎；大语言模型；Agentic Workflow；React；Go

## Abstract

With the rapid growth of digital transformation and business automation, traditional hand-coded software development and data processing methods increasingly suffer from long development cycles, high maintenance costs, and poor agility. Low-code platforms reduce the barrier to building applications through visual modeling, while large language models further enable natural-language-driven system construction. To address the lack of integration among visual orchestration, AI-based workflow generation, complex web data acquisition, private deployment, and platform governance in existing solutions, this paper designs and implements a low-code intelligent workflow platform named YaoLight Workshop based on Go and React.

The system adopts a front-end/back-end separated architecture. The front end is implemented with React 19, TypeScript, React Flow, and Ant Design to provide a visual workflow editor and interactive user interface. The back end is implemented with Go, Gin, GORM, PostgreSQL, and Redis to support workflow execution and platform services. The platform focuses on workflow modeling, execution, scheduling, and intelligent generation, and provides eleven node types, including start, crawler, data cleaning, AI processing, condition, transform, loop, merge, delay, output, and end. It supports workflow editing, execution, streaming feedback, task logging, artifact export, and open API publishing. For intelligent generation, this paper designs an AI assistant named Alkaid, which introduces an Agentic Workflow mechanism that combines capability description, knowledge retrieval, tool invocation, trial execution, patch repair, and human confirmation to transform natural language requirements into executable workflows.

Compared with conventional low-code platforms, the proposed system has the following features: a DAG-based concurrent workflow execution engine, a source-code-driven capability extraction mechanism to reduce AI hallucination risks, a human-in-the-loop patch confirmation mechanism, and an integrated platform architecture that unifies open APIs, artifact export, notifications, billing, and RBAC governance. Finally, the paper discusses the system from the perspectives of functional correctness, representative execution scenarios, and extensibility, and presents its current limitations and future improvements.

**Key Words:** low-code; workflow engine; large language model; Agentic Workflow; React; Go

## 第1章 绪论

### 1.1 研究背景

在数字经济背景下，企业软件系统已从单一的信息录入与查询工具逐步发展为面向业务流程协同、数据采集处理和智能决策支持的综合平台。传统的软件开发方式通常需要前端、后端、数据库和运维人员协同完成，开发门槛较高，迭代周期较长。当业务需求频繁变化，或者用户只希望快速搭建一个“采集数据—清洗处理—模型分析—导出结果”的自动化流程时，纯代码开发模式往往成本过高。

低代码技术为这一问题提供了有效思路。通过节点拖拽、可视化连线和配置式建模，复杂流程可以被抽象为图结构，并在统一引擎中执行。与此同时，大语言模型在自然语言理解、代码生成、工具调用和任务规划等方面表现出越来越强的能力，使“用户用一句话描述需求，系统自动生成工作流”的交互方式成为可能。尤其在数据采集与 AI 内容处理场景中，用户往往并不关心代码细节，而更关心任务是否能够稳定执行、结果是否可导出、系统是否便于后续修改。

然而，现有低代码平台和 AI 应用构建平台仍存在明显不足。一类平台擅长审批流与表单驱动业务，但对复杂网页抓取、动态渲染和多节点数据处理支持不足；另一类平台专注于大模型应用构建，但对通用工作流执行、调度治理和工程化平台能力覆盖不够。基于此，设计一个融合可视化工作流、并发执行引擎、多模型接入、网页爬虫、AI 自动生成、开放 API 与平台治理能力的一体化系统，既具有研究意义，也具有实际应用价值。

### 1.2 国内外研究现状

低代码与工作流技术的发展已较为成熟。国内外大量平台通过图形化建模提升了开发效率，但多数系统在能力边界上有所偏重。传统低代码平台更适合表单、审批和数据录入场景，强调业务人员参与；自动化平台则更强调第三方服务集成和任务触发；而新一代大模型应用平台更关注 Prompt、知识库和智能体编排。总体而言，真正将“低代码工作流 + 通用爬虫 + 多模型 AI + 平台治理”系统化融合的工程型研究成果仍然较少。

在 AI 辅助工作流生成方向，已有研究开始尝试利用大语言模型生成结构化流程定义，并通过提示约束、检索增强和格式校验提高生成质量。但许多方案仍停留在一次性输出层面，对生成后的逻辑校验、试运行验证、失败修复以及人机协同确认的研究不足。对于需要真正落地执行的工作流系统而言，仅靠单次 JSON 生成并不足以保证可用性。

在系统架构层面，前后端分离与模块化服务组织已成为主流实践。以 React 等现代前端框架负责交互和可视化建模，以 Go、Java 或 Node.js 等后端框架负责服务编排、存储和执行控制，能够兼顾开发效率和运行性能。如果再结合 PostgreSQL 对复杂 JSON 数据结构的支持，以及 Redis 在缓存和运行时状态上的辅助能力，便可为低代码工作流平台提供较好的实现基础。

### 1.3 研究目的与意义

本文的研究目标是设计并实现一个面向数据采集、内容处理与智能分析场景的低代码智能工作流平台“瑶光工坊”。系统不仅支持用户通过可视化方式搭建工作流，还支持通过自然语言由 AI 助手自动生成工作流，并对生成结果进行校验、试跑和人工确认，从而降低非专业用户使用复杂自动化能力的门槛。

本课题的理论意义在于：探索低代码工作流平台与大语言模型深度融合的实现路径，验证“自然语言到工作流”的工程闭环是否可行，并为 AI 辅助软件工程和智能流程编排提供实证案例。本课题的实践意义在于：将多模型调用、网页爬虫、数据清洗、任务调度、结果导出和开放接口等能力整合到统一平台中，形成一个具备真实业务承载能力的系统原型，可服务于舆情监测、竞品分析、信息采集和内容自动化生成等场景。

### 1.4 本文主要工作与创新点

本文围绕系统需求分析、总体架构设计、数据库设计、工作流引擎实现、AI 助手设计与平台治理能力构建等方面开展研究，完成了一个可运行的全栈系统。与一般课程设计或单体功能原型不同，本系统不仅包含工作流编辑器，还包含用户端、管理后台、开放 API、任务监控、通知、计费和权限治理等支撑能力。

本文的主要创新点体现在以下几个方面：

1. 提出并实现了面向低代码工作流平台的 Agentic 生成闭环。系统不是简单依赖单次大模型生成，而是将能力说明、知识检索、工具调用、试跑校验、失败修复和人工确认整合为一个可解释、可追踪的生成流程。
2. 设计了基于源码配置抽取的能力说明机制。系统通过配置抽取器从节点执行源码中提取配置字段、默认值和变量引用特征，用于动态更新 Alkaid 的能力说明，减少文档与代码不一致导致的生成错误。
3. 实现了支持并发执行的工作流引擎。系统以图结构描述流程，结合依赖判断、节点状态管理、节点执行记录和任务日志记录，实现了从单节点执行到整图并发调度的统一控制。
4. 构建了待确认工作流与待确认补丁机制。AI 生成结果不会直接写入画布，而是先进入待确认区，用户可选择整图应用或补丁应用，增强了系统安全性与可控性。
5. 将开放 API、工件导出、账务计费、通知与 RBAC 融入平台级架构，形成了具备工程完整性的低代码系统，而非仅面向演示的单点功能实现。

## 第2章 相关技术与理论基础

### 2.1 React 与可视化工作流编辑技术

本系统前端采用 React 19 与 TypeScript 进行开发。React 具有组件化、状态驱动和生态成熟等特点，适合构建交互复杂、状态较多的单页应用。结合 React Router 可实现多页面前端路由组织，结合 Zustand 可进行局部状态与共享状态管理。

工作流编辑器部分采用 React Flow 作为核心可视化编排库。React Flow 支持节点拖拽、边连接、缩放平移、自定义节点渲染和句柄控制，适合表达工作流这种图结构数据。系统在此基础上进一步封装了 11 类节点组件、对应的配置面板和节点测试能力，实现了从图形交互到业务配置的统一界面。

### 2.2 Go、Gin 与 GORM 技术基础

后端采用 Go 语言实现。Go 天然支持高并发编程，语法简洁，部署方便，适合构建高吞吐、低延迟的服务系统。Gin 是 Go 生态中常用的轻量级 Web 框架，具有中间件机制清晰、路由性能良好等特点，适合承载认证、工作流接口、开放 API 和管理接口等多种 HTTP 服务。

数据访问层使用 GORM 完成对象关系映射。GORM 通过模型定义、关联查询和自动迁移降低了数据库操作复杂度，并支持 JSONB 等类型扩展，能够适配工作流节点配置、AI 参数和通知元数据等结构化与半结构化并存的数据形态。

### 2.3 PostgreSQL、Redis 与平台数据管理

PostgreSQL 作为系统主数据库，承担用户、项目、工作流、任务、AI 模型、知识库、通知、订单与权限等核心数据的持久化。相比传统只存储关系型字段的数据库设计，本系统大量使用 JSONB 存储节点配置、模型参数、工件元数据、运行上下文等动态结构，既保持了表结构稳定性，又保留了较高的扩展性。

Redis 主要用于缓存与临时状态支持，例如验证码、OAuth 绑定过程中的临时状态等。对于需要高频读取但不要求长期落盘的场景，Redis 可降低数据库访问压力，提升系统响应速度。

### 2.4 工作流引擎与 DAG 执行思想

工作流本质上可以看作由节点和有向边构成的图结构。节点表示处理步骤，边表示数据依赖或控制依赖。对于无循环主链流程，可以视作 DAG（有向无环图）进行依赖调度；对于包含条件和循环的场景，则需要在运行时结合分支状态和输入数据进行动态控制。

本系统的工作流引擎采用“节点配置 + 边关系 + 变量上下文”的设计方式。执行时，系统先构建节点与边关系，再根据上游节点执行状态判断下游节点是否就绪；对于 AI 节点可启用流式输出，对于条件节点则通过分支句柄决定执行路径。为提高吞吐量，系统还设计了并发执行流程，对无依赖冲突的节点进行并行调度。

### 2.5 大语言模型、RAG 与 Agentic Workflow

大语言模型为低代码平台带来了全新的交互方式。用户可以不再手工拖拽每一个节点，而是通过自然语言描述目标任务，让系统自动生成流程框架与节点参数。然而，直接让模型输出工作流 JSON 容易产生幻觉、漏字段、结构错误和场景不匹配等问题。

为此，系统引入 Agentic Workflow 思路，将 AI 助手从“文本生成器”升级为“带工具的工作流规划者”。在该模式下，模型不直接生成最终结果，而是先读取平台能力说明，再结合知识库检索、节点规格查询、URL 可访问性检查、工作流试跑等工具逐步收集上下文，最后输出待确认工作流或补丁。与此同时，系统还通过知识检索与规则注入对提示词进行增强，这一过程可视为面向平台规则的轻量 RAG。

### 2.6 ChromeDP 动态网页爬虫技术

网络数据采集是本系统的重要使用场景之一。静态页面可通过 HTTP 请求与解析器获取，但大量现代网站依赖 JavaScript 动态渲染，普通请求方式难以获得完整内容。为此，系统采用 ChromeDP 实现无头浏览器抓取，从而支持动态页面加载、页面等待、HTML 获取和相关扩展能力。

为了提高爬虫节点的可用性，系统还引入了 URL 可访问性检查、超时设置、重试控制、请求头与 Cookie 配置等机制，并通过后台爬虫规则管理实现抓取经验的沉淀与复用。

### 2.7 SSE、WebSocket 与实时反馈技术

工作流执行与 AI 会话都具有明显的实时性需求。用户希望在执行过程中看到节点状态变化、日志和中间结果，而不是等到所有流程结束后一次性返回。为满足该需求，系统在工作流执行与 Alkaid Agentic 会话中采用 SSE 进行流式推送，在站内通知模块中采用 WebSocket 推送消息，从而形成面向不同场景的实时反馈机制。

## 第3章 系统分析与总体设计

### 3.1 系统角色分析

从业务角度看，系统主要包含三类角色。第一类是普通用户，负责创建项目、维护工作流、执行任务、调用 AI 助手和查看导出结果；第二类是管理员，负责模板、节点类型、爬虫规则、AI 模型、账务和通知等平台级资源治理；第三类是外部系统调用方，其通过已发布的 Workflow API 调用指定工作流并获取执行结果或工件。

### 3.2 功能需求分析

系统的核心功能需求可以概括为以下几个方面。

首先是工作流建模需求。用户需要通过拖拽节点和连接边快速构建自动化流程，并在图形界面中完成节点参数配置、变量引用和流程调整。系统应支持至少开始、爬虫、数据清洗、AI、条件、转换、循环、合并、延迟、输出和结束等节点类型。

其次是工作流执行与监控需求。系统不仅要能够执行工作流，还要记录任务运行状态、节点执行结果、错误信息和任务日志，并支持在前端实时展示执行进度。

再次是 AI 辅助生成需求。用户希望通过自然语言直接表达目标，由 Alkaid 自动生成流程，并在生成过程中理解节点能力、结合知识库检索结果进行规划，在必要时通过试跑和修复机制提高生成成功率。

此外，系统还需要覆盖项目资产管理、多模型接入、开放 API、站内通知、支付与计费、后台管理和权限控制等平台级支撑需求，以支撑真实使用场景。

### 3.3 非功能需求分析

非功能需求主要体现在以下几个方面：

- **可扩展性**：节点类型、AI 提供商、输出格式和后台管理能力应支持持续扩展。
- **可维护性**：系统需采用明确的模块边界，降低多功能平台后期演进成本。
- **可用性**：AI 生成结果不能直接覆盖用户画布，必须保留人工确认能力。
- **可观测性**：需要具备任务日志、节点执行记录、通知和操作日志等追踪能力。
- **性能与并发性**：执行引擎应支持并发调度与长任务运行。
- **安全性**：接口需具备 JWT、API Key、RBAC 与 Hook 风控等多层控制。

### 3.4 系统总体架构设计

系统总体采用前后台分离架构，并进一步拆分出独立的管理后台前端。整体可分为四层。

第一层是用户交互层，包括普通用户前台和管理后台。普通用户前台负责项目、工作流、AI 助手、任务结果和个人中心等功能；管理后台负责平台级资源和治理能力。

第二层是接口服务层，由 Gin 提供统一 REST API，同时在部分场景下扩展 SSE 和 WebSocket。该层承接登录认证、工作流操作、任务执行、通知推送和后台管理等请求。

第三层是业务服务层，由多个模块组成，包括用户、项目、工作流、任务、AI、Alkaid、支付、账务、通知、权限、系统治理和开放 API 等。各模块以相对独立的方式组织，形成模块化 DDD 风格后端。

第四层是数据与基础设施层，包括 PostgreSQL、Redis、本地或对象存储型文件系统、外部 AI Provider 接口和外部网站资源。工作流执行结果和导出文件统一沉淀为 Artifact，以便复用。

### 3.5 数据库总体设计

从数据库设计上看，系统不是围绕单一业务对象设计，而是围绕平台能力进行建模。全系统共涉及 47 张核心表，可分为用户认证、RBAC、项目工作流、任务调度、AI 模型与计费、Alkaid 知识与会话、爬虫与资产、开放 API、通知、订单与系统治理等多个表组。

其中，`workflows`、`workflow_nodes` 和 `workflow_versions` 共同描述工作流的主体数据；`tasks`、`task_node_executions`、`task_logs`、`task_schedules` 和 `task_schedule_runs` 描述执行与调度过程；`alkaid_sessions`、`alkaid_messages`、`alkaid_knowledge` 和 `alkaid_node_specs` 支撑 AI 助手；`workflow_api_endpoints`、`workflow_api_keys` 与 `workflow_api_invocations` 支撑外部调用；`artifacts` 则统一管理输出文件和导出结果。

### 3.6 模块划分设计

后端以模块化方式组织，主要模块包括 `user`、`project`、`workflow`、`task`、`ai`、`alkaid`、`crawler`、`artifact`、`file`、`payment`、`billing`、`notification`、`rbac`、`node`、`system` 和 `workflowapi` 等。每个模块通常包含模型、仓储、服务和控制器，既利于理解也利于后续演进。

前端则按照页面、组件、状态与 API 分层组织。其中工作流编辑器是核心复杂组件，内部再按照节点组件、配置面板、输出提供商和 AI 提供商进行扩展式设计。

## 第4章 系统详细设计与实现

### 4.1 用户与权限模块设计

用户模块提供注册、登录、邮箱验证码验证、OAuth 登录、密码重置、头像管理和个人资料维护等能力。用户实体除用户名、邮箱、密码等基础字段外，还维护 Token 余额、邀请关系、OAuth 绑定状态和偏好设置等信息。系统同时通过邀请码与邀请记录支持邀请裂变场景。

权限治理部分采用 RBAC 模式实现。系统通过 `roles`、`permissions`、`role_permissions` 和 `user_roles` 四张表实现管理员角色与资源权限控制。管理后台各接口通过权限中间件进行校验，不同资源采用 `resource:action` 风格的细粒度权限编码，实现用户管理、模型管理、任务查看、账务操作和通知发送等能力的差异化控制。

### 4.2 工作流建模模块设计

工作流建模部分以前端可视化画布为核心。用户在编辑器中拖拽节点、配置参数并建立边连接，前端将图结构以节点数组和边数组形式保存到后端。后端在保存时会将每个节点转化为 `workflow_nodes` 表中的持久化记录，并根据边关系构建连接信息。同时，系统还支持注释卡片，用于在画布中记录说明、备注和设计思路，从而提升复杂流程的可维护性。

在节点设计上，系统支持 11 类节点，覆盖从输入、采集、清洗、AI 处理、分支控制到输出结束的完整链路。开始节点用于定义初始输入，爬虫节点负责采集网页内容，数据清洗节点用于清理和标准化文本，AI 节点负责大模型处理，条件节点决定分支，转换节点进行映射或过滤，循环节点处理数组输入，合并节点汇聚多路数据，延迟节点控制时间，输出节点负责结果导出，结束节点则标记流程终止。

### 4.3 变量上下文与数据流设计

为了支持节点之间的数据传递，系统设计了变量上下文机制。每个节点执行结束后，会将自身输出写入变量上下文，并按 `nodeId.variableName` 形式建立索引。下游节点可通过 `{{nodeId.variableName}}` 或更深层路径形式引用上游结果。对于对象类型数据，系统可进一步解析字段路径，实现例如 `{{start-1.data.url}}` 这样的嵌套访问。

这一设计使工作流中的节点不再依赖硬编码输入，而是可以围绕统一数据流动态拼接，从而提高了可组合性和复用性。与此同时，变量上下文还为 AI 节点、条件节点和转换节点的配置模板解析提供了基础支撑。

### 4.4 工作流执行引擎设计

工作流执行引擎是系统后端的核心部分。执行时，系统首先根据节点和边构建执行请求，然后识别开始节点，初始化数据流与变量上下文，再按节点依赖关系调度下游节点。与简单的串行执行不同，系统实现了并发执行逻辑：对于依赖已满足且互不冲突的节点，可同时进入执行状态，从而提高整体执行效率。

引擎对任务级和节点级状态分别进行记录。任务层通过 `tasks` 表记录整体运行状态、输入、输出、错误信息和耗时；节点层通过 `task_node_executions` 表记录每个节点的输入、输出、状态、错误和执行时长；日志层通过 `task_logs` 表记录调试、信息、警告和错误日志。这样既支持前端实时展示，也为管理员排查问题提供了数据基础。

在控制流方面，条件节点依赖边上的句柄区分真假分支；循环节点用于遍历数组并汇总结果；合并节点基于输入句柄汇聚多路结果；延迟节点实现时间控制。这些机制共同保证了系统能够覆盖较复杂的业务流程。

### 4.5 任务调度与触发设计

除手动执行外，系统还支持定时调度与触发运行。调度模块使用 `task_schedules` 表存储计划任务信息，包括 Cron 表达式、时区、激活状态、最大运行次数、下次执行时间、Webhook Token、输入模板和通知配置等内容；`task_schedule_runs` 表则记录每次调度触发的执行明细。

系统提供两类典型触发方式：一类是基于 Cron 的定时调度，适合周期性采集与处理任务；另一类是基于 Webhook Token 的外部触发，适合与第三方系统联动。调度服务在后台持续运行，根据任务计划自动触发工作流执行，并将结果纳入统一任务体系进行管理。

### 4.6 AI 模型适配与模型治理设计

系统在 AI 能力接入上采用 Provider 抽象。前端 AI 节点支持通过注册表动态加载不同提供商配置组件，后端则通过提供商工厂与统一接口封装各类模型调用差异。当前系统已覆盖 DeepSeek、豆包、通义千问、智谱、讯飞星火、腾讯混元以及经 OpenRouter 接入的 GPT、Claude、Gemini、Grok 等模型来源，同时保留 OpenAI 官方接入能力。

值得注意的是，系统将“用户自定义模型配置”和“平台管理模型主数据”进行了区分。普通用户侧通过 `ai_models` 管理自身可调用模型；平台管理侧则通过 `managed_ai_models`、`model_capability_configs`、`model_pricing_configs` 和 `model_pricing_rules` 维护统一的能力与计费配置。这种分层设计有利于后续实现模型治理、运营和成本分析。

### 4.7 Alkaid 智能助手设计与实现

Alkaid 是本文最具特色的模块之一。系统并未将其设计为单纯的聊天框，而是将其设计为一个面向工作流生成的 Agentic 助手。会话层通过 `alkaid_sessions` 和 `alkaid_messages` 持久化用户会话、消息内容和中间状态；知识层通过 `alkaid_knowledge` 和 `alkaid_node_specs` 管理通用知识、项目知识、工作流级知识和节点规格约束。

在执行链路上，Alkaid 会先读取能力说明，再结合知识检索、当前工作流上下文、节点规格查询、URL 可访问性检查等工具逐步规划，随后生成待确认工作流或待确认补丁。系统通过 SSE 向前端持续推送阶段变更、计划步骤、工具步骤、生成内容以及待确认结果，实现“过程可见”的智能交互体验。

为减少 AI 生成错误，系统引入了多重保护机制。首先，`CapabilitiesService` 提供结构化节点能力说明；其次，`config_extractor` 可从节点执行源码中自动抽取配置字段和默认值；再次，Alkaid 在生成后还可以触发试跑与错误反馈，并在需要时调用补丁机制对现有工作流进行增量修改。最后，在写回画布前，系统还支持 `BeforeApplyWorkflow` 等 Hook 进行风控和人工确认。

### 4.8 能力说明自动抽取机制

传统 AI 应用在平台场景中存在一个常见问题，即“提示词中写的规则”和“后端真正支持的配置”逐步偏离。为解决这一问题，本文设计了配置抽取器。该组件会扫描工作流节点执行源码中的配置读取逻辑，如 `getString`、`getInt`、`getBool` 等调用，提取字段名、默认值和变量引用特征，并据此更新能力说明服务中的规则集合。

这种机制虽然不是完整编译器级 AST 推理，但在工程实践中有效减少了知识滞后和文档漂移问题。对于论文而言，这一实现可以作为“AI 生成可靠性增强”的一个重要创新点。

### 4.9 爬虫与数据处理模块设计

爬虫能力既体现在工作流节点中，也体现在后台规则管理中。工作流中的爬虫节点可配置 URL、请求方式、抽取模式、抽取类型、超时与重试等参数，并支持变量引用；后台中的爬虫规则则可沉淀抓取经验，包括 URL 匹配规则、请求头、参数、Cookie、分页策略和数据抽取规则等。

在 Alkaid 的智能生成过程中，系统还会优先对用户提供的候选网址执行可访问性检查，避免将搜索页、登录页或不可抓取页面直接写入工作流。这一机制提升了爬虫工作流的首轮可运行率，也体现了系统面向真实业务场景的工程考虑。

数据处理部分则通过数据清洗节点和转换节点完成。前者偏重文本与内容规范化，后者偏重结构重组、字段映射和列表操作，两者与 AI 节点组合后能够形成较完整的数据处理链路。

### 4.10 输出工件与开放 API 设计

系统的输出节点并非简单返回文本，而是通过导出工厂统一生成 Artifact。后端导出工厂支持 JSON、Markdown、Text、PDF、DOCX、Mermaid、Timeline、Sankey、Network 以及 Chart(SVG) 等格式，前端输出节点则通过注册表方式选择格式与投递目标。所有输出结果最终都可以沉淀为 `artifacts` 记录，支持预览、下载、邮件发送和对外 API 获取。

在开放能力方面，系统允许用户将工作流发布为可调用 API。发布后，系统会为工作流生成唯一 Slug，支持 API Key 创建、同步或异步调用、调用记录查询、状态查询和工件下载。这样，工作流不再只是平台内的交互对象，也可以作为外部系统可复用的服务能力。

### 4.11 通知、账务与系统治理设计

为了提升平台完整性，系统还集成了多项平台级支撑能力。通知模块支持站内通知、通知模板、批量发送、发送任务和投递记录；账务模块支持订单管理、Token 流水、配额恢复和管理员赠送；系统治理模块支持管理员操作日志和统计数据沉淀。这些能力虽然不是论文的主算法部分，但对于说明系统具有工程化完整性十分关键。

## 第5章 系统测试

### 5.1 测试目标

系统测试的目标主要包括以下几个方面：验证工作流编辑、保存与加载是否正确；验证各类节点在典型场景下是否可执行；验证任务调度、日志记录和工件导出是否稳定；验证 Alkaid 生成流程是否能够在主流场景下正确生成待确认工作流或补丁；验证平台治理能力如权限控制、通知和开放 API 是否满足基本业务要求。

### 5.2 功能测试设计

功能测试可按照模块划分开展。

1. 用户模块测试：注册、登录、邮箱验证码、OAuth 登录、修改密码、头像管理、邀请链接等。
2. 项目与工作流测试：项目创建、工作流新建、节点保存、连线保存、注释卡片保存、模板读取等。
3. 执行引擎测试：单节点执行、链式执行、条件分支执行、循环执行、合并节点执行和并发执行。
4. AI 助手测试：普通会话、Agentic 会话、待确认工作流生成、补丁生成、写回画布。
5. 开放能力测试：Workflow API 发布、API Key 调用、异步返回、工件下载。
6. 管理功能测试：模板管理、节点类型管理、爬虫规则管理、AI 模型管理、任务监控、通知发送与权限控制。

### 5.3 典型流程测试方案

本文建议选取以下典型业务流程作为实验案例：

1. **网页信息采集与总结流程**：开始节点输入目标网址，爬虫节点抓取正文，数据清洗节点去除噪声，AI 节点完成总结，输出节点导出 Markdown 或 PDF。
2. **批量列表处理流程**：开始节点输入数组数据，循环节点遍历，AI 节点逐项分析，合并节点整合结果，输出节点导出 JSON。
3. **AI 自动生成流程**：用户通过自然语言描述目标任务，Alkaid 自动生成工作流，进行试跑和修复后，用户确认写回画布。
4. **开放 API 调用流程**：已发布的工作流通过 API Key 被外部系统调用，系统返回结果或提供工件下载地址。

### 5.5 系统不足分析

尽管系统已覆盖较完整的平台能力，但当前仍有以下不足：

1. 部分管理端能力仍在持续完善，例如系统配置页前端仍为占位实现。
2. AI 生成链路虽然已经具备多轮规划和补丁机制，但在复杂长链工作流场景下，生成质量仍依赖模型能力与知识覆盖度。
3. 输出与图表能力已具备基础实现，但在排版美观性、模板多样性和复杂图表适配方面仍有提升空间。
4. 当前测试数据和性能指标需要进一步标准化采集，以便形成更完整的定量评估。

## 第6章 总结与展望

本文围绕低代码工作流、AI 自动生成、网页数据采集和平台工程治理等需求，设计并实现了一个基于 Go 与 React 的低代码智能工作流平台“瑶光工坊”。系统不仅完成了可视化编辑器、并发执行引擎、任务调度、多模型接入和导出能力的实现，还进一步构建了 Alkaid 智能助手，将自然语言需求解析、能力说明、知识检索、工具调用、试跑校验、补丁修复和人工确认整合为一个完整闭环。

从系统实现结果来看，本文的工作表明：低代码平台与大语言模型并非只能松散耦合，而可以通过规则注入、能力抽取、试跑反馈和平台治理机制进行深度融合；工作流系统也不应只关注“画布能否画出来”，还应关注任务能否监控、结果能否导出、接口能否开放、权限能否治理。正是在这一思路下，“瑶光工坊”从一个单一功能原型发展为具有较强工程完整性的综合平台。

后续工作可从以下几个方面展开。第一，继续提升 Alkaid 在复杂流程场景下的规划与修复能力，引入更细粒度的自动评估机制。第二，完善系统配置中心、更多后台治理页面和更多对象存储后端支持。第三，增强图表导出、模板市场和多租户能力，使平台更适合真实业务部署。第四，补充更系统的性能测试与用户可用性研究，以形成更完整的实证评估。

综上所述，本文完成的系统具有较强的研究价值与实践意义，为低代码平台与 AI 智能体结合提供了一个较完整的工程实现样本。
