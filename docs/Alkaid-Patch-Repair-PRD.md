# 瑶光星 AI 助手一键修复与补丁预览 PRD

| 项目 | 说明 |
|------|------|
| 产品名称 | 瑶光星 AI 助手一键修复 |
| 文档版本 | 1.0 |
| 适用范围 | `Low_code_Frontend`、`Low_code_Backend` |
| 更新日期 | 2026-03-14 |
| 文档目标 | 用单一 PRD 收口瑶光星“失败诊断、补丁生成、补丁预览、用户确认、应用修复”的完整产品方案 |

---

## 1. 背景

当前瑶光星已经具备以下能力：

- 在 Agentic 对话中生成工作流
- 将生成结果以待确认工作流或待确认补丁的形式推送给前端
- 用户可点击“应用到画布”或“应用补丁”

但“一键修复”能力仍明显不完整，主要问题如下：

- 前端只展示 `patchCount`，用户不知道具体改了哪些节点、哪些边、哪些配置
- 没有真正的“修复入口”，用户无法在失败上下文中自然触发“让瑶光星帮我修”
- 没有画布级预览，用户确认前无法直观看到即将发生的改动
- 修复结果缺少可解释性，用户容易担心 AI 静默改错地方
- 失败诊断、补丁提议、补丁应用之间是分裂的，不是完整闭环

这会直接影响两个核心目标：

- 用户对“一键修复”的信任
- 用户愿不愿意为失败后的二次修复继续消耗算力和成本

因此需要将“补丁修复”从一个技术实现点，升级为一个完整产品能力。

---

## 2. 产品目标

### 2.1 核心目标

让用户在工作流执行失败、校验失败或配置不合理时，可以通过瑶光星完成以下闭环：

1. 看懂为什么失败
2. 看懂 AI 打算怎么修
3. 在不污染当前画布的前提下预览改动
4. 明确确认后再应用补丁
5. 应用后获得清晰反馈

### 2.2 成功定义

用户在失败场景下，不需要手动排查 JSON 或节点配置，也能完成一次可信、可解释、可确认的修复。

---

## 3. 非目标

本期不追求以下目标：

- 完全自动静默修复并直接写入画布
- 无限次自动重试直到跑通
- 覆盖所有复杂冲突合并场景
- 在本期内实现完整的可视化 patch diff 编辑器
- 替代现有工作流编辑器的所有手工修图能力

---

## 4. 用户与场景

### 4.1 目标用户

- 不熟悉节点参数和连线规则的普通用户
- 能描述需求但不擅长手动排错的业务用户
- 使用瑶光星快速搭建工作流的高频用户

### 4.2 核心场景

#### 场景 A：运行失败后修复

用户运行工作流失败，希望瑶光星分析错误并给出可应用补丁。

#### 场景 B：生成后发现结构不合理

用户看到工作流能导入但不够合理，希望瑶光星在当前画布基础上做小范围修正，而不是整图重生。

#### 场景 C：局部节点配置错误

用户知道是某个节点出问题，但不确定怎么改，希望瑶光星直接提出局部 patch。

---

## 5. 当前问题定义

### 5.1 当前前端能力不足

当前前端更接近“待确认补丁最小壳子”，而不是完整修复产品：

- 只显示“待确认补丁：N 项变更”
- 只有“应用补丁 / 放弃”
- 没有补丁明细
- 没有节点级解释
- 没有画布预览
- 没有失败上下文入口

### 5.2 当前用户风险

- 不知道 AI 改了什么，不敢点“应用补丁”
- 看不到改动范围，担心破坏现有画布
- 失败后不知道下一步该做什么
- 长链路修复成本高，用户容易放弃

---

## 6. 产品方案概述

本期将“一键修复”定义为以下五段式闭环：

1. 失败检测
2. 失败诊断
3. 补丁生成
4. 补丁预览与确认
5. 补丁应用与结果反馈

其中最重要的原则是：

- AI 可以提出修改建议
- 用户必须确认后才能真正写入画布
- 所有修复应尽量以 patch 形式呈现，而不是整图覆盖

---

## 7. 功能范围

### 7.1 本期必须实现

#### F1. 失败上下文中的修复入口

在以下位置提供“让瑶光星修复”入口：

- 工作流执行失败后
- 节点测试失败后
- 校验失败后
- 瑶光星对话中已经存在失败上下文时

#### F2. 结构化补丁提议

瑶光星输出的修复结果必须优先是 patch，而不是整份 workflow。

补丁至少支持：

- 新增节点
- 删除节点
- 修改节点配置
- 修改节点位置
- 更新边集合

#### F3. 待确认补丁明细

前端不再只显示 `patchCount`，而是至少展示：

- 将新增哪些节点
- 将删除哪些节点
- 将修改哪些节点
- 是否会改动边

#### F4. 画布预览

收到待确认补丁后，在不写库、不真正修改当前画布数据的前提下，对画布进行只读预览高亮：

- 新增节点：绿色或虚线高亮
- 删除节点：红色或半透明高亮
- 修改节点：黄色高亮
- 边变化：轻量提示或边高亮

#### F5. 用户确认后应用补丁

用户点击“应用补丁”后：

- 后端执行 patch 应用
- 保存到当前工作流
- 清空 pendingPatch
- 返回成功反馈

#### F6. 放弃补丁

用户点击“放弃”后：

- 清空当前会话的 pendingPatch
- 清空前端预览状态

#### F7. 修复反馈

补丁应用后，前端要明确反馈：

- 已应用成功
- 应用了哪些类别的改动
- 如需要，可引导用户重新运行或继续让瑶光星优化

## 8. 分阶段版本定义

### 8.1 V1：可信可用版

目标：先把“敢用”做出来。

包括：

- 失败场景下触发补丁修复
- `pending_patch` 返回结构化 summary
- 前端补丁详情卡片
- 画布只读预览
- 应用补丁 / 放弃

### 8.2 V2：增强版

目标：把“好用”做出来。

包括：

- 节点级失败原因解释
- 更细粒度 patch 明细
- 可定位到具体节点与字段
- 用户从失败节点一键发起修复

### 8.3 V3：闭环版

目标：把“像一个真正的修复助手”做出来。

包括：

- 应用 patch 后可选自动重试
- 自动重试失败后继续诊断
- 输出“已修复并跑通”或“无法自动修复，需要补充信息”

---

## 9. 核心用户流程

### 9.1 运行失败后的修复流程

1. 用户运行工作流失败
2. 前端展示失败信息与“让瑶光星修复”
3. 瑶光星读取当前工作流与失败上下文
4. 瑶光星输出 patch 提议
5. 后端写入会话 `pendingPatch`
6. 前端展示补丁明细与画布预览
7. 用户点击“应用补丁”或“放弃”
8. 若应用成功，画布更新并提示结果

### 9.2 对话中直接修复当前画布

1. 用户说“帮我修一下这个工作流”
2. 瑶光星读取当前画布
3. 识别修复意图并生成 patch
4. 进入待确认补丁流程

---

## 10. 前端需求

### 10.1 待确认补丁卡片升级

当前卡片需要升级为以下信息结构：

- 标题：待确认修复补丁
- 摘要：共 N 项变更
- 新增节点列表
- 删除节点列表
- 修改节点列表
- 边是否变更
- 可选原因说明
- 操作按钮：应用补丁、放弃

### 10.2 画布预览状态

前端需要维护一个独立于真实画布数据的预览态，例如：

- `addedNodeIds`
- `removedNodeIds`
- `updatedNodeIds`
- `edgesChanged`

要求：

- 预览态只影响 UI，不直接改真实画布数据
- 切换会话、应用补丁、放弃补丁时必须清空

### 10.3 失败入口

以下位置应能触发修复：

- 执行失败面板
- 节点测试失败面板
- 瑶光星聊天区域
- 后续可扩展到节点右键菜单

### 10.4 状态反馈

前端需要明确区分：

- 正在诊断
- 正在生成补丁
- 待确认补丁
- 应用补丁中
- 补丁应用成功
- 补丁应用失败

---

## 11. 后端需求

### 11.1 pending_patch 事件升级

当前 `pending_patch` 仅返回：

```json
{ "patchCount": 3 }
```

本期目标升级为：

```json
{
  "patchCount": 3,
  "summary": {
    "addedNodeIds": ["node-7"],
    "removedNodeIds": ["node-3"],
    "updatedNodeIds": ["node-5"],
    "edgesChanged": true
  }
}
```

### 11.2 会话态补丁数据

会话中应保留完整 `pendingPatch`，用于：

- 前端应用补丁
- 前端查看详情
- 调试与排查

### 11.3 补丁生成原则

后端在修复场景下应优先返回 patch，而非整份 workflow。

### 11.4 补丁应用原则

后端执行 `apply-patch` 时必须：

- 校验 workflow 归属
- 从 session 读取 pendingPatch
- 应用 patch 到当前工作流
- 保存节点与边
- 清空 pendingPatch

### 11.5 错误处理

需要区分：

- patch 生成失败
- patch 解析失败
- patch 应用失败
- 当前工作流已变化导致 patch 不再适用

## 12. 数据结构要求

### 12.1 PatchItem

建议维持现有 patch 概念，并明确支持：

- `add`
- `remove`
- `set`
- `set_edges`

### 12.2 SSEPendingPatch

建议定义：

```ts
interface SSEPendingPatch {
  patchCount: number;
  summary?: {
    addedNodeIds?: string[];
    removedNodeIds?: string[];
    updatedNodeIds?: string[];
    edgesChanged?: boolean;
  };
}
```

### 12.3 前端预览结构

```ts
interface PatchPreview {
  addedNodeIds?: string[];
  removedNodeIds?: string[];
  updatedNodeIds?: string[];
  edgesChanged?: boolean;
}
```

---

## 13. 交互规则

### 13.1 用户确认原则

- 所有 patch 默认不自动应用
- 所有写画布行为必须用户确认

### 13.2 覆盖规则

若会话中连续收到多次 `pending_patch`：

- 前端只保留最后一次 patch 预览
- 之前的 patch 预览自动失效

### 13.3 大补丁降级策略

当 patchCount 很大时：

- 卡片只展示摘要与 Top N 节点
- 画布预览只做轻量提示
- 避免一次渲染过多高亮造成卡顿

### 13.4 会话切换规则

切换会话时需要清空：

- patch 预览态
- 应用中状态
- 当前待确认 patch 展示

---

## 14. 文案要求

用户可见文案需要满足：

- 清楚说明“为什么修”
- 清楚说明“修哪里”
- 清楚说明“不会自动改，需你确认”

示例：

- “瑶光星发现当前工作流存在可修复问题，已为你生成修复补丁。”
- “将新增 1 个节点、修改 2 个节点，并更新部分连线。”
- “确认后才会写入当前画布。”

---

## 15. 风险与挑战

### 15.1 用户信任风险

如果补丁说明不透明，用户不敢点“应用补丁”。

### 15.2 画布一致性风险

如果 pendingPatch 生成后，用户手动修改了当前画布，可能导致补丁不再适用。

### 15.3 大补丁渲染压力

一次大范围修复可能导致前端预览高亮过重。

### 15.4 修复意图误判

用户有时只是想看建议，不一定想立即得到 patch。

---

## 16. 验收标准

### 16.1 V1 验收

- 失败场景下可以触发瑶光星修复
- 后端能返回结构化 `pending_patch summary`
- 前端待确认补丁卡片可展示明细
- 画布可以做只读预览高亮
- 用户可应用补丁或放弃补丁
- 应用后画布正确更新

### 16.2 体验验收

- 用户无需读 JSON，也能理解修复将发生什么
- 用户不会在确认前误以为画布已被改动
- 用户在失败后知道下一步该怎么做

---

## 17. 建议排期

### 第一阶段

- 后端 `pending_patch` summary
- 前端补丁明细卡片
- 应用/放弃闭环

### 第二阶段

- 画布预览高亮
- 失败入口整合

### 第三阶段

- 应用后自动重试
- 失败后继续诊断

---

## 18. 结论

“一键修复”不是一个按钮，而是一套“失败诊断 + patch 解释 + 预览 + 用户确认 + 应用”的可信闭环。

本 PRD 的目标不是让瑶光星偷偷改图，而是让用户在失败场景下，能够低风险地接受 AI 修复建议，并清楚知道每一步发生了什么。
